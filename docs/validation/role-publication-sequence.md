# F2 连续发布链验收操作

本流程验证同一固定规则窗口中的逐日角色发布，不是订单换月，也不认证交易所全市场完备。通过离线用例不等于通过真实多日验收。

## 开始前

固定品种、合约资料、候选范围、算法参数、初始主力和覆盖整个验收窗口的交易时间版本。确保资料中所有窗口候选身份有效，时间包含末日决定的下一生效开盘。窗口内改变这些输入应开始新的独立验收，当前接口不提供跨规则状态交接。

首日按时采集全部当日存续候选的日线。保留每份已发布版本，不以较晚累计快照替换旧输入。用 `computed/preview` 构造单日结果，确认资料及日线可知时间、计划生效开盘，再经 `POST /api/v1/contract-roles/computed` 发布并保存返回的版本 ID。所有后续步骤使用账户/PIN 保护的 API。

首日应在计划开盘前完成真实发布。周末补采历史日线只能证明本机此时可知；若它和下一个正常观测日指向同一开盘，就不能作为连续验收首日。不得改时间以绕过拒绝。

## 每个后续交易日

1. 使用原固定身份资料采集该日全部存续候选日线，保存当前发布版本 ID。缺失行不是零成交，不能跳过。
2. 调用 `POST /api/v1/contract-roles/computed/continue-preview`，明确 `previous_version_id`、本次一个交易日的 `daily_inputs` 和 `explanation`。
3. 服务端重验前一版本来源及其发布资格，保留原始窗口与初始状态，追加新日并重算确认过程。缺口、重复、历史输入替换、规则变化或生效日重叠均拒绝。预览本身不发布。
4. 把返回的完整 `ComputedSpec` 提交已有计算发布接口，保存新版本 ID。相同内容重复提交保持第一次发布时间。不要用重建一份单日请求代替续算，否则它是新的独立计算窗口。
5. 按实际顺序把从首日开始的版本 ID 提交 `POST /api/v1/contract-roles/computed/sequence/verify`。`minimum_switches=0` 用于检查尚未发生换月的进展；验收换月必须明确要求至少 1 次。未达到要求返回失败，不将“没有切换”称作换月成功。

续算只增加待发布内容，不自动调度、不下单、不改变已有版本。发布接口保留实际服务器时间；事后验收会拒绝晚于新增决定计划开盘的发布。不要通过删除迟到记录或改写发布时间伪造连续性。

## 证据与当前状态

保存固定资料与逐日日线、各次计算版本和发布时间、确认过程、来源重建及发布链验收结果。发布链逐项验证来源，数学重放不能替代来源核验。读取错误、校验和变化或必要规则缺失时停止该项验收。

2026-09-20 当前实现已通过离线两日接口集成：首日等待确认、次日实际切换；已覆盖无换月门槛、重置规则、替换历史版本、缺失候选、倒序、迟到重叠和来源篡改。真实单日的 12 候选采集发布已通过；真实连续多日发布与自算换月尚未通过，没有设置后台定时采集任务。


## 通过任务执行续算

新接口 `POST /api/v1/contract-roles/computed/tasks` 接受 `command_id` 与 `continuation`（结构与续算预览相同）。调用方先取得该日全部已发布日线版本，再提交；接口准入时重建并冻结前序版本、续算请求和预期计算结果。它不负责自动触发数据源同步，也不是定时器。

Worker 通过注册的 `contract_roles.continue` 处理器重放固定输入，按通用任务协议回传。角色插件在发布端重验来源、前序版本和租约，确认新增决定能按时生效后，在同一事务写入不可变角色版本与任务完成结果。重复回传相同结果不改变首次发布时间；结果变化、失效租约、来源变化、晚于计划开盘均拒绝。

`GET /api/v1/contract-roles/computed/tasks/{id}` 返回任务状态与成功结果中的 `computed_version_id`、`previous_version_id`，不返回租约令牌或内部载荷。失败任务可调用 `POST /api/v1/contract-roles/computed/tasks/{id}/retry`；重试保持固定输入，每个失败任务只有一个后继，重复请求复用该后继。租约过期后重新领取仍由核心机制处理；业务插件不自行续租或绕过租约。

任务中心由角色插件贡献“合约角色续算”和“重试续算”，成功时显示版本标识。排队及历史任务的固定行情输入计入资料引用，不能因结果尚未发布就丢失依赖。登记同步任务后的自动衔接见下一节；自动定时采集和初始发布配置界面仍未实现。


## 同步发布后自动入队

`POST /api/v1/contract-roles/computed/sync-workflows` 登记一个交易日的衔接工作流。请求必须提供 `command_id`、`previous_version_id`、`trading_day`、全部候选的 `sync_job_ids` 和说明。调用方先通过现有数据同步入口提交各候选日线任务，再登记这些任务 ID；不需要等待同步完成或手工传递行情版本 ID。

角色插件通过数据公开能力核验任务确为同来源、同固定资料、同观测日的日线同步，且精确覆盖所有当日存续候选。日期必须为固定时间契约中的下一个观测交易日。只完成部分候选时等待；最后一份日线提交时，在同一事务内重建计算输入、保存续算任务 ID 并入队。重复通知或重复登记同一命令不创建第二个任务。登记前已全部完成也能衔接；登记与完成并发通过依赖任务锁保护。

`GET /api/v1/contract-roles/computed/sync-workflows/{id}` 只读返回登记信息、各同步任务状态、错误和续算任务 ID。GET 不触发执行。进程重启后日线完成通知读取同一持久工作流；不会依赖内存订阅。

日线发布与工作流推进使用同一个数据库事务。同步任务失败或取消不会入队；来源内容、确认窗口或时点检查失败时，保留已经成功采集的数据，并在工作流记录错误。工作流固定依赖具体同步任务；失败任务重试产生新任务 ID 时，调用方必须明确用新任务集合登记新的工作流，不自动追踪可能改变输入的任务链。

新增通用机制 `Storage.join(transaction)` 只让持有存储授权的插件在可写事务中写自己的表；只读事务、已关闭事务、其他数据库以及越权表写入仍拒绝。原 `borrow` 保持只读。该机制是为跨插件原子衔接所需，核心没有识别数据源、合约角色或期货规则。

已提交同步任务可以自动衔接，也可使用下面的批量入口一次创建并登记。每天何时开始采集和首次计算发布仍未自动化；没有启用定时器，也没有新增真实连续多日换月证据。


## 一次提交全部候选

`POST /api/v1/contract-roles/computed/sync-batches` 接受 `command_id`、`previous_version_id`、`trading_day`、`connection_id` 和 `explanation`。`connection_id` 必须明确传入连接标识或 `null`（使用该数据源默认配置）。响应为同一持久工作流回执；通过上述 GET 查询进度。

角色插件从固定前序版本和合约生命周期确定下一观测日的全部存续候选，经 `data.daily_sync_batch` 调用数据插件。数据插件从供应商能力声明解析日线接口，逐个执行标准同步准入、身份核验和配置冻结。全部同步任务与工作流登记在同一事务提交；任何候选不合格或登记失败，都不留下部分任务。冻结配置文件可能已写入，但失败事务不会产生可执行任务。

相同命令和输入再次提交复用回执，不重复采集，也不重新冻结连接配置；同一命令更换前序版本、日期、说明或连接明确拒绝。该入口依赖已有按时发布的前序版本，不创建初始计算版本，不替代交易日历或自动推算节假日。单个同步任务失败后的处理仍遵循上节的显式新工作流规则。


## 在角色面板提交与查看

数据工作区 → 合约角色 → 计算角色，选择已发布版本后展开“采集与续算”。后端 `GET computed/{id}/sync-plan` 重验固定来源及前序发布，按唯一时间契约给出下一观测交易日和存续候选；界面不使用自然日加一或重新解释节假日。此查询不创建任务，正式提交时重新核验。

选择同来源、已配置且启用的连接，点击“采集并续算”。面板为每个前序版本使用固定命令标识，提交错误后锁定输入并提供“重试原请求”；服务端幂等回执避免丢失响应时重复采集。面板通过 `GET computed/{id}/sync-workflows` 恢复已登记记录；已有记录时仅查看，不自动开启第二批。连接配置仍在数据源设置管理。

候选同步状态、固定行情版本、续算状态与新角色版本标识分别显示。面板打开且服务连接时轮询，隐藏、断开或结束后停止；进度读取失败明确显示，保留最近结果并重试。即使新计划因来源核验失败无法读取，已有记录仍可查看。刷新不会提交任务。

当前面板不自动首发、不设置定时器、不重登记失败采集链；采集失败或取消会明确提示需在重试后登记新任务集合。新发布版本可通过角色列表刷新查看。真实连续采集与换月证据仍按实际交易时间验收。
