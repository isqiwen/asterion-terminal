开发前产品规格 · 2026-10-20。本页定义产品目标、功能边界、共同业务规则及模块责任，供需求评审、UI设计、开发交接和验收设计使用。

## 需求依据与设计边界

| 来源                   | 需求依据                                                                              | 对本文的约束                                                                                             |
| ---------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 用户的产品定位         | 个人期货研究与实盘交易并重                                                              | 研究与交易均须形成完整使用闭环，不以其中一方代替另一方                                                   |
| 用户的量化范围         | 规则策略与多因子组合两者都覆盖                                                          | 两条主线都必须从定义、验证走到资金仓位、受控执行与复盘；自动化量化执行属于核心能力，具体方法按模块交付范围编制，签认另记 |
| 用户确认的数据模块划分 | 数据接入与采集、数据加工与质量、数据管理与服务                                          | 基础资料纳入管理与服务；质量与追溯贯穿三者，不形成第四个一级模块；按业务责任定义需求                   |
| 用户的文档要求         | 详细讲解、案例及做成后的样子，补齐各种界面设计和操作流程                                | 图与案例一致；必须有页面字段、按钮行为和逐步流程，不能只给功能清单或需求关系图                           |
| 用户的编写要求         | 需求先于产品                                                                            | 业务需求从用户任务推导；定义目标导航、页面、操作、状态与未来验收；不依赖产品实现情况       |
| 项目范围约束           | 期货；macOS Apple Silicon 与 Linux x86_64 桌面；远程运行仅 Linux x86_64，服务于桌面使用 | 不扩展 Web、移动端、Notebook、独立命令行客户端或 Windows 桌面                                            |
| 项目数据和交易约束     | 真实数据来源；交易授权及风险控制；断线不自动重发；凭据保护；用户资料不可静默改写或删除  | 作为各项需求必须遵守的安全边界                                                                           |

主导航定义为数据、情报、分析、策略、回测、评估、实盘七个入口，二级导航对应子模块，系统管理为独立辅助入口。页面及承载方式见[界面设计总览](common/ui-designs.md)，视觉、控件和键盘规则见[UI设计约定](common/interaction.md#ui-design-contract)。

产品定位与任务构成需求依据；正文的具体方法、交互和质量阈值是可评审的设计规格。设计修改须记录理由和影响，不能把作者编写视为使用者逐项签认。案例数字为虚构输入，用于手工推演和编写验收用例，不是市场事实、盈利承诺或交易默认值。

## 使用者、问题与目标

使用者为一位独立完成数据准备、策略研究、交易决策、运行监控和事后复盘的个人。研究者、交易者和维护者是同一人的不同任务视角，不据此引入团队权限体系。

| 任务视角         | 需要解决的问题                             | 预期价值                                   | 如何判断目标是否满足                                         |
| ---------------- | ------------------------------------------ | ------------------------------------------ | ------------------------------------------------------------ |
| 规则量化研究     | 交易逻辑不明确、试算难定位、参数试验难复核 | 将交易假设变为可检查的规则与独立验证的候选 | 从信号能定位可得输入和判断规则，从结论能复核全部试验条件     |
| 多因子与组合研究 | 因子冗余、样本泄漏、评分无法转为可交易仓位 | 解释因子合成、资金预算与组合目标的形成依据 | 能核对训练冻结、样本外表现、整数手数、保证金和组合约束       |
| 交易             | 下单意图含糊、状态不明、风险约束缺失       | 在明确账户、合约、数量和风险边界内执行     | 每笔委托能解释授权、校验、外部反馈及最终状态                 |
| 研究进入交易     | 好看的回测结果被直接当作可交易证明         | 用独立验证和明确授权决定是否进入实盘       | 研究候选、模拟观察、实盘授权各自有清楚的依据                 |
| 量化运行与复盘   | 实盘表现偏离研究结论却无法定位原因         | 从信号、目标、委托、成交到持仓逐层调查差异 | 区分数据、逻辑、执行和成本差异，明确暂停、核对及重新验证范围 |
| 日常维护         | 长任务、连接中断和资料管理打断工作         | 能辨认状态、保留成果、处理故障并继续工作   | 已保存资料可追溯，结果不明时有明确核对路径                   |

本软件帮助使用者判断与执行，不承诺盈利，不把历史表现当作未来收益保证。收益指标只是研究和复盘材料；任何实盘操作仍受交易授权、账户状态及风险规则约束。

## 核心模块阅读顺序与数据路径

| 顺序 | 核心模块 | 主要职责                                   |
| ---- | -------- | ------------------------------------------ |
| 1    | 数据     | 获取、加工、保存及提供可靠材料和标准数据   |
| 2    | 情报     | 将需要语义理解的材料转为带证据的结构化情报 |
| 3    | 分析     | 探索规律、构建变量并检验有效性             |
| 4    | 策略     | 定义决策、组合及仓位规则                   |
| 5    | 回测     | 模拟历史交易和账户演变                     |
| 6    | 评估     | 判断绩效、风险和结论可靠性                 |
| 7    | 实盘交易 | 管理真实运行、执行及账户事实               |

行情和标准化库存等输入走“数据 → 分析”；公告、新闻和研报等需要语义加工的材料走“数据 → 情报 → 分析”。目录顺序不表示所有数据都必须经过情报。实盘结果可返回评估，研究结论可返回分析和策略继续验证。系统管理作为支撑模块列于七个核心业务模块之后；风险要求分别归属策略、回测、评估和实盘，公共交互和可视化要求归通用规范。

## 范围与优先级

首个发布只交付其中一条闭环，范围见[首个发布切片 R1](release-r1.md)。

数据模块按三个子模块组织，详细职责、8 项界面对应及目标业务流程见[数据模块详细设计](modules/data/README.md)。[从采集到研究输入](workflows/README.md#jrn-001)可用于逐步评审；[实时中断与补采](workflows/README.md#jrn-002)和[修订与依赖保护](workflows/README.md#jrn-003)用于检查异常。

### 功能范围

- 数据与量化研发：真实来源接入、合约及连续规则、历史数据和质量、研究假设、规则与因子定义、试算和错误定位、期货回测、批量参数实验、稳健性及样本外验证。
- 多因子与组合：时点样本池、因子处理及评价、相关性与冗余、合成规则及训练冻结、组合权重、资金与风险预算、整数目标手数、调仓差额和贡献归因。
- 量化执行与风控：研究/模拟/实盘逻辑和状态核对、策略与组合授权、统一执行、运行状态与偏差归因、账户及组合风险控制、受控暂停和恢复。自动执行是核心产品范围；策略频率、组合方法与运行条件见模块交付范围，风险及研究门槛按用户必填配置核对。
- 交易观察与人工操作：实时行情、自选与图表、手动委托、订单成交、资金持仓和对账；人工操作与自动运行共享账户事实及风险边界。
- 日常使用：桌面安装与准备、长任务管理、本地及远程运行归属、数据保存与恢复、凭据保护、可理解的错误、资料导出和可测量的质量目标。

不纳入本产品范围：非期货交易、团队协作审批、多租户运营、资金托管、跟单销售、社交推荐，以及未经确认的数据购买或外部付费服务。“量化”不自动引入机器学习平台、高频低延迟承诺、Notebook 客户端或完整内嵌开发环境。支持的数据类型、逻辑形式、模型和交易行为在各模块的有限能力集合中列明；具体提供方须满足[外部能力要求](delivery.md#delivery-gates)。

### 优先级含义

| 级别       | 含义                                                     | 排序依据                                           |
| ---------- | -------------------------------------------------------- | -------------------------------------------------- |
| P0安全必要 | 缺失会导致错误交易、越权、结果被误认为可信或重要资料受损 | 对应能力启用前必须满足；不等于其他业务能力可以缺失 |
| P1核心必要 | 完成个人研究或交易主要任务所必需                         | 研究与交易同级评审，按用户任务完整性确定范围       |
| P2条件增强 | 适用于已明确但非普遍的使用条件                           | 明确适用条件后按对应规格提供             |

优先级是需求建议，不是开发排期。规则策略与多因子组合均属于核心范围，自动执行属于明确的功能范围。两条主线的方法、频率、容量及本地/远程运行条件均须明确；依赖关系用于组织开发，不改变完整需求范围。

## 关键使用场景

### 完成一次可复核的期货研究

| 步骤 | 使用者要做的事                                       | 必须得到的结果                       |
| ---- | ---------------------------------------------------- | ------------------------------------ |
| 1    | 记录研究问题，例如某信号能否在交易成本后仍有区分能力 | 明确假设、样本范围和判断标准         |
| 2    | 选择合约范围、数据来源和时间区间                     | 知道权限、覆盖范围、费用和数据口径   |
| 3    | 检查缺口、异常、修订与连续合约处理                   | 知道哪些样本可用，哪些条件会影响结论 |
| 4    | 固定输入、策略、费用及风险条件并运行实验             | 获得可复现、带完整性说明的结果       |
| 5    | 比较参数和样本外结果，解释收益与风险                 | 比较不混淆不同数据、区间或成本条件   |
| 6    | 记录结论、局限和是否形成交易候选                     | 即使结论是否定的，也能保留推理依据   |

### 完成两类量化任务

| 量化主线   | 连续操作                                                                                                                                                       | 必须留下的结果                                                                                                      |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 规则策略   | 写明入场、退出及仓位规则，验证输入可得性；用固定小样本试算并定位错误；预览参数空间和预算；批量回测并检查失败样本、参数邻域与成本扰动；进行独立验证，再形成候选 | 逻辑内容身份、试算证据、全部尝试及筛选过程、冻结候选、验证局限和授权边界；不能仅留下收益最高的一行                  |
| 多因子组合 | 固定时点样本池和数据；检查因子覆盖、方向及相关性；限定训练区间拟合处理和合成权重；冻结后验证；将评分和约束转为权重、整数手数与调仓差额；模拟后显式授权运行     | 因子处理与拟合记录、样本外结果、组合分配规则、资金/保证金核算、目标与实际仓位及贡献归因；因子有效性不等于组合可交易 |

两条主线共用数据、风险、执行和记录规则。规则策略也可纳入组合，多因子组合也必须产生明确的交易目标。相同数据和状态下应能核对逻辑输出；不同环境的成交和收益不承诺相同。详细字段、异常和虚构案例见[量化工作流程](modules/strategy/README.md)。

### 完成一次有明确结果的手动交易

| 步骤 | 使用者要做的事                           | 必须得到的结果                               |
| ---- | ---------------------------------------- | -------------------------------------------- |
| 1    | 选择账户和交易环境，完成交易授权         | 行情已连接不能被误认为交易已获授权           |
| 2    | 查看合约规则、行情时效、资金与持仓       | 明确本次操作的上下文和不可用信息             |
| 3    | 输入方向、开平意图、数量、价格及有效条件 | 提交前可辨认完整交易意图及风险影响           |
| 4    | 提交并观察委托反馈                       | 区分本地拒绝、待确认、已受理、部分成交等状态 |
| 5    | 按需要撤销剩余委托或等待成交             | 撤单申请不等同于已经撤单，已成交部分保留     |
| 6    | 核对成交、持仓、资金及费用               | 结果可以解释；有差异时明确进入核对流程       |

### 将研究候选用于量化自动交易

使用者先确认候选对应的数据、规则/因子及组合条件，核对相同信息和状态下的信号与目标，再观察模拟执行、失败行为和风险约束。拟进入实盘时，必须确认账户、逻辑内容、参数、风险规则及资金额度，取得明确授权。启动后从信号追踪到目标、委托、成交和持仓，能调查数据时点、执行和成本偏差。暂停新增、撤单、平仓与停止运行分别说明范围；历史研究、模拟成功或账户曾获授权，都不能单独代替本次实盘授权。四种运行模式与启用条件按本页及实盘功能范围核对。真实交易采用有人值守模式；离开监控前须暂停新增风险并处理、核对在途订单和持仓。关闭窗口本身不构成暂停或停止。

### 面对断线、退出和资料恢复

行情失效时说明最后有效时点；交易结果不明时保存待核对意图，查询外部状态，不自动补发。关闭窗口前能够理解仍在运行的任务与交易活动；明确停止运行与只关闭显示界面的差别。恢复资料时先验证完整性及目标位置，不静默覆盖原有账户记录、任务或数据集。每种异常都应指出使用者可以采取的下一步。

## 全局业务定义与规则

这些规则适用于所有需求；条目中的更细规则不得削弱它们。

| 编号             | 规则                                                                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| BR-01 合约身份   | 显示名称便于辨认，交易所、品种和到期身份用于区分合约；相似代码或连续序列不得被当作同一可交易合约。来源不足以唯一识别时不能猜测下单对象。                       |
| BR-02 时间       | 区分事件发生时间、接收时间、所属交易日和显示时区。夜盘的交易日归属以已确认的数据源及交易规则为准；不能直接按自然日推断。                                       |
| BR-03 缺失值     | 未提供、无权限、尚未加载、过期、无成交和有效数值零分别表达。不能把未知金额或缺失行情显示成有效零，也不能制造行情填补展示。                                     |
| BR-04 数值口径   | 价格、金额、数量、比例均说明单位与精度；计算使用准确的业务数值。展示舍入不能改变下单价格、风险判断或账务金额；费用与结算按账户及合约适用规则解释。             |
| BR-05 数据来源   | 生产数据来自获得授权的数据服务。记录来源、覆盖范围、时间口径和修订信息；文档示例与测试样本不能流入真实研究或交易数据。                                         |
| BR-06 研究证据   | 结果关联实际使用的数据、策略、参数、费用和风险条件。输入改变产生新的实验记录；不得在旧结果中悄悄换用新数据或新参数。                                           |
| BR-07 授权与风险 | 所有实盘执行均要求明确授权和可用的账户风险规则。缺少任一前置条件时拒绝执行，并解释缺少什么。回测及策略模拟缺少必要风险配置或风险能力不可用时，也必须拒绝执行。 |
| BR-08 交易事实   | 提交意图、外部受理、成交与撤销是不同事实。未知结果不能推断为失败，也不能推断为成功；重复反馈不能重复计算成交与资金。                                           |
| BR-09 断线       | 断线与重连不构成重新发送交易命令的授权。先核对外部事实，再由用户明确决定后续新操作；不得把重发隐藏在自动恢复中。                                               |
| BR-10 资料保护   | 保存和恢复须有明确结果；不得静默改写、迁移或删除用户资料。删除前说明对象与影响；有效依赖存在时禁止删除，确认弹窗不能覆盖依赖保护。故障处置不能隐含清理资料。                                             |
| BR-11 凭据       | 凭据由用户本地输入或生成，不能进入普通配置、日志或共享资料。仅在用户选择时保存允许保存的行情凭据至系统安全凭据存储，不复用于交易登录。                         |
| BR-12 可解释状态 | 失败、取消、部分完成、结果待核对分别显示；每个状态说明对结果可信性或执行权限的影响，并给出与该异常直接相关的继续方式。                                         |
| BR-13 信息可得性 | 样本资格、因子输入、拟合、规则判断及调仓均使用当时可得的信息。拟合和选参记录实际使用区间；已用于选择的验证资料不能继续标为未接触样本。                         |
| BR-14 组合口径   | 因子评分、权重、目标手数、实际持仓、名义敞口、保证金和现金分别表达。账户层合并风险与策略层贡献可核对；相反策略信号不能在无明确归属规则时默默净额处理。         |

## 案例图与验收的使用方式

业务算例图解释金额计算、订单事件和结果对照；目标页面图定义信息层级、字段、按钮和状态，两者配合阅读。示例合约A/B、账户甲/乙和案例日T/T+1仅用于推演。合约乘数、手续费、风险阈值和成交条件按案例给定假设计算，不代表市场规则或默认值。图与正文不一致时应同时修正，不能选择较容易实现的一种解释。

目标界面浏览按业务导航和UI编号组织。每张页面图对应一项UI规范，状态图补充空、加载、失败、过期、待核对等分支；静态图中的示例值不替代字段约束。

验收条件采用“给定 / 当 / 则”。验收编号使用需求编号加 `AC` 序号，例如 `REQ-LIV-EXE-01-AC01`。这些条目定义未来验证行为的标准。外部服务与柜台按交付准入核验，账户风险为必填运行配置，硬件负载和性能目标按非功能基线测量；没有实际证据不能判定通过。

功能和页面另有 `FR-…-AC…`、`UI-…-AC…` 验收编号，分别检查操作结果和界面行为。旅程用完成标准检查跨页面任务是否闭环。不能因单页能显示、原型能点击或某条验收通过，就推定整个用户任务成立。

## 评审、变更与维护

只维护一套当前有效的需求。已被替代或废弃的需求、页面方案和案例直接更新或删除，不保留旧版副本、兼容入口或失效索引。正文、目标界面浏览、图片和阅读版必须指向同一套当前要求；变更历史通过 Git 提交记录，不另存历史需求包。尚未解决的需求、待确认事项和有效评审意见继续保留。

1. 先确认目标用户、市场范围和关键使用场景，再逐项检查输入、操作、结果及异常是否完整。
2. 对每项DEC记录规格决定、运行配置或交付准入。规格由本次授权编制，未取得逐项答复时不标为用户确认；用户限额和真实外部证据不能由作者代填。
3. 编制版用于评审、设计交接和开发估算；用户签认后作为正式验收基线。后续变更说明变更原因与受影响条目，使用同一需求编号；编号不因文案调整而变化，也不复用于不同需求。
4. 模块正文是需求规则和评审记录的唯一维护入口。评审意见、答复、确认状态和确认日期直接记录在对应条目旁；确认后的决定落实到要求、操作流程和验收条件，决定登记页由正文同步生成索引。未确认意见不自动改变要求。
5. 案例图、目标界面图、操作旅程和图文阅读版随正文同步更新。需求正文定义目标行为；后续执行记录在评审文档中管理，不写回需求正文作为产品状态说明。

每次评审以一个旅程为单位检查：入口是否能找到、必要信息能否输入、动作前提和后果是否清楚、成功后能否继续、失败后能否处理、退出后保留什么、验收是否可观察。发现缺口时补到相应 FR / UI / JRN，而不是仅在总纲追加一句“支持某功能”。本规格给出有限方法集合与可测质量指标；来源、柜台和发行条件按约定取得验收证据。

首次评审建议以规则策略、多因子组合两条旅程展开：确认市场及数据范围、策略定义方式和频率、批量规模、因子处理与合成方法、资金分配及调仓规则、量化运行门槛和风险阈值，再确认本地/远程运行及容量负载。目标与方法分别确认，不能把核心方向已确认等同于每种算法都已批准。

## 情报的职责范围

产品设置独立的[情报](modules/intelligence/README.md)，下设信息提取、情报核验、事件服务。核心任务是把非结构化和半结构化来源材料转为有证据、时间语义和核验状态的结构化情报，原生考虑LLM处理、方法评测与受控使用。

核心业务模块按“数据 → 情报 → 分析 → 策略 → 回测 → 评估 → 实盘交易”组织，情报位于数据之后、分析之前；系统管理提供运行支撑，风险要求分布于策略、回测、评估和实盘，不设独立风险控制模块。可视化按公共交互能力组织，开发者工程工具不在本次新增独立业务模块。

数据负责获授权采集、原始材料、基础解析、通用资料和统一保存访问；情报负责语义解释、映射判断、证据核验、事件组织及发布决定。供应商标准结构化基本面可直接进入分析。分析检验事件变量的预测价值，策略定义决策，交易仍要求授权、风险配置和统一执行。

材料获取、提取、核验、发布、交付及执行状态必须独立可解释；原文不能被修正候选覆盖。处理记录保留模型、提示、输入和实际时间；未知信息不补造，来源观点与推断单独标识。历史重处理不冒充当时可得信息，材料中的指令不获得系统操作权限。

新增材料到研究、更正与时点查询、模型失败和质量检查三条旅程。材料格式、提取/核验和发布规则见情报交付范围；模型位置、费用和外发许可为显式配置，来源能力须核验。情报页面的输入、核验、发布和研究交接应采用独立状态。

## 分析模块的职责范围

分析为第三个核心业务模块，阅读顺序位于数据与情报之后，下设“数据探索与统计分析、特征与因子构建、有效性评估与筛选”。[分析模块](modules/analysis/README.md)负责规律与变量证据；完整策略历史模拟归[回测模块](modules/backtest/README.md)，绩效与可靠性评价归[评估模块](modules/evaluation/README.md)，策略候选与固定内容交付归[策略模块](modules/strategy/README.md)。算法和容量按功能范围与非功能基线定义，研究筛选门槛由使用者事前填写。

## 策略与回测的职责范围

第四个核心业务模块为策略，下设“策略逻辑构建、组合与仓位管理、策略管理与交付”；第五个核心业务模块为独立回测。规则、模型和混合方式统一纳入策略逻辑构建，历史模拟放在回测，绩效与验证结论放在评估，实盘运行控制和账户授权仍由交易负责。目标导航对应业务模块；业务划分不直接决定服务进程。

## 回测与评估的职责范围

第六个核心业务模块为“评估”，下设“绩效度量与归因、风险分析与压力测试、稳健性验证与综合评价”。回测保留“回测设计与实验管理、交易与账户模拟”两个子模块，提供固定实验与模拟事实；评估统一服务回测、模拟交易及实盘。报告为三类评估共用输出，不单列业务子模块。真实交易事实、账户风险政策与控制权限均由实盘负责。具体方法、格式及容量按模块交付范围编制，研究/账户阈值须显式配置。

## 实盘交易模块的职责范围

第七个核心业务模块为实盘交易（Live Trading），下设“实盘准备与运行管理、订单执行与成交管理、账户管理与交易核对”。真实执行和账户事实归本模块，绩效、风险分析与跨环境归因仍归评估；账户风险政策、实时准入及运行限制归入本模块的相应子模块。实盘、仿真柜台与本地模拟的环境和授权分别表达，不能因复用机制而混称。详情见[实盘交易](modules/live/README.md)。可视化属于各业务页面与通用规范，不另设业务模块。

<a id="execution-risk-semantics"></a>

## 风险要求的业务归属与共用交易约束

产品保持七个核心业务模块和系统管理，不设独立风险控制模块或风控中心。风险职责直接嵌入策略定义、回测执行、风险评估和实盘操作；本节集中定义共用含义，各业务章节保存自己的操作与验收，避免维护多份同义规则。

| 责任方                    | 唯一负责的业务内容                                                          | 不得替代的职责                                   |
| ------------------------- | --------------------------------------------------------------------------- | ------------------------------------------------ |
| 策略 / 组合与仓位管理     | 策略预算、目标仓位、集中度、止损或暂停条件及触发后的目标变化                | 策略自身合规不能放宽账户政策或取得交易权限       |
| 回测 / 实验管理与账户模拟 | 固定模拟账户风险参数、执行规则含义、检查能力和触发处置，并记录模拟拒绝/成交 | 不跳过必要风险配置；不访问或修改真实账户规则     |
| 评估 / 风险分析与压力测试 | 回撤、波动、敞口、尾部及压力评价，解释规则触发和执行差异                    | 不直接修改实盘限额、暂停、撤单或平仓             |
| 实盘 / 账户管理与交易核对 | 实际账户政策、配置资格、规则生效及变更影响                                  | 不由策略或报告代为放宽                           |
| 实盘 / 订单执行与成交管理 | 统一逐笔准入、资金及在途占用、并发额度判断、订单结果核对与占用释放          | 手动与策略入口不互相绕过，不复用过期的通过结论   |
| 实盘 / 准备与运行管理     | 账户风险预警、运行限制、暂停及恢复、残余风险处置入口                        | 停止策略不代表撤单或平仓，标记告警已读不解除限制 |

每份规则须明确身份和实际内容、适用范围、指标单位与基准、输入时效、阈值、在途口径、触发行为及恢复条件；引用规则的具体定义和生效记录，不用名称相同冒充内容相同。风险算法通过插件提供，执行边界保证必要检查，不增设独立产品模块或服务进程。

回测与实盘复用规则定义及检查语义，参数可以不同，但差异须显式固定和展示；模拟依据模拟账户与历史输入，实盘依据真实账户及当前有效输入。同一规则、参数和有效业务状态下，应能解释相同的准入结果；不能承诺不同数据、时序或成交条件下一定得到相同结果。规则定义复用不意味着共享可变额度或真实账户状态。

策略目标或预览通过都不是账户交易许可。实盘提交仍核对账户授权、有效政策、所需输入及可用风险插件；回测也必须具有必要配置与可执行插件，模拟不需要真实交易授权。缺配置或检查能力时拒绝执行，不能切换试跑、手动入口或以“减仓”为名绕过新的委托检查。

持仓、在途订单和新意图按声明口径计入风险，占用和准入共同决定，避免多个请求重复使用同一剩余额度。撤单申请或外部结果不明不等于容量可释放；释放依据已确认订单事实。风险拒绝不自动改量改价，恢复或断线重连不自动重发旧交易命令。

预警、暂停新增、停止策略、撤单、平仓和恢复各有明确后果。阻止新增风险不取消已有订单，平仓仍可能失败或部分成交；安全查询与独立合规撤单按各自权限保留。风险检查不依赖用户打开某个页面或先生成评估报告。

示例：策略允许本次新增3手，但账户已持仓2手、在途开仓1手、潜在同方向上限5手，则实际新增3手得到6手并拒绝。模拟若采用相同参数和有效状态，也记录同样拒绝；评估解释策略意图与执行结果差异，不修改规则。案例上限仅用于说明，不是推荐参数。

完整交接见[风险约束业务流程](workflows/README.md#jrn-034)。

## 日志、配置、调度与告警的协作

七个核心业务模块和系统管理的划分不变。系统管理提供运行日志检索、系统配置与配置索引、定时触发和公共运行能力；各模块拥有业务配置、任务含义、执行状态和告警触发/解除。通知中心按公共交互规范提供统一呈现，不另设风控与告警大模块。

| 需求类别   | 公共职责                                      | 业务职责                                                               |
| ---------- | --------------------------------------------- | ---------------------------------------------------------------------- |
| 日志       | 运行诊断、检索、明确留存和最小脱敏导出        | 材料证据、实验、账户与交易事实及操作审计不依赖普通日志留存             |
| 配置       | 节点、连接、插件、凭据机制、通用偏好和索引    | 数据来源用途、情报模型方案、策略参数、实验条件、账户限额在所属模块生效 |
| 定时任务   | 运行位置、时区/日历、触发记录、错过和重叠处理 | 内容、实际输入范围、授权预算、风险及执行结果由业务判断                 |
| 风险与告警 | 通知统一展示、阅读状态、渠道与静音            | 策略/回测/评估/实盘按既有职责控制或分析风险；各业务确认自己的告警状态  |

保存不等于生效，已调度不等于已完成，日志不等于账本，已读不等于告警解除。统一入口不引入第二份业务配置和状态。计划恢复不能补发交易指令，通知失败不能阻止必要风险控制，日志清理不能删除业务记录与证据。

配置和日志见[系统管理](modules/system/README.md)，通知见[公共通知规范](common/interaction.md#req-com-ux-02)。能力范围、质量目标与工作台规格由对应模块维护。

## 功能支持范围与跨模块交付

本规格在“个人期货研究与实盘并重、规则策略与多因子均覆盖”的范围内补齐行为，不将所有市场、算法或柜台自动纳入。每种范围内能力必须明确支持集合、输入要求、业务输出、限制和验收依据；“可扩展”不能代替有限功能定义，案例中出现的方法也不等于默认支持承诺。

| 能力范围 | 必须在具体交付清单中列明 | 未满足时的功能行为 |
| --- | --- | --- |
| 数据来源 | 市场、真实合约、数据类型、频率、历史区间、历史规则、时间字段、授权与消耗依据 | 不支持或未核实分别显示；阻止依赖缺项的取数/研究，不伪造替代输入 |
| 情报 | 材料类型、事件结构、字段含义、核验与发布条件、质量评测覆盖 | 结构不合法进入失败/待补；证据不足保留候选，自动发布缺门槛则不可启用 |
| 分析 | 特征/标签表达、预处理与拟合、统计评价、样本条件和时点约束 | 参数与输入可检查；方法不可用或样本不足明确拒绝/不可判定，不输出假数值 |
| 策略 | 规则表达方式、算子、模型训练与预测方法、信号到目标映射、组合政策、状态初始化和退出 | 草稿可保存；缺必需定义不得固定可执行包；因子验证不能替代策略验证 |
| 回测 | 时序、订单、撮合、费用、保证金/结算、换月及期末规则、支持账户范围 | 不支持的订单/规则不被忽略或替换；不可观察路径依赖事前声明假设 |
| 评估 | 公式与参数、单位、年化/基准/现金流、最小样本、压力方法、结论及报告条件 | 无定义、缺资料、未计算和0分开；不同口径不直接排名 |
| 运行 | 本地实时模拟、外部柜台仿真、实盘各自能力；账户归属、数据依赖、跨日条件、授权和恢复 | 模式明确，输入缺项拒绝；研究/模拟成功不生成真实权限，未知交易先核对 |
| 系统 | 平台最低要求、安装产物、节点信任、插件能力、配置生效、资料保护及凭据可用位置 | 安装、连接、可信、业务就绪分别反馈；不支持资料保留原件并拒绝使用 |

有限方法和支持范围在各模块README的“交付范围”统一维护，性能见[非功能验收基线](common/reliability.md#quality-baseline)，设计决定与配置要求见[决定与配置登记](decisions.md)。设计变更须保留评审依据；来源、柜台、模型和发行能力按[外部能力要求](delivery.md#delivery-gates)核验。

### 交付对象与唯一责任

| 交付对象 | 产生及维护方 | 消费方必须核对 |
| --- | --- | --- |
| 固定数据及实时输入契约 | 数据 | 实际内容、单位、可得时点、质量、用途和连续性 |
| 带证据的已发布情报 | 情报；原始材料及统一存取由数据负责 | 发布与撤回时点、证据、用途、实际历史/事后模式 |
| 因子/条件与研究候选 | 分析 | 定义、样本和拟合身份、选择记录、验证限制；不是完整策略 |
| 固定策略包与仓位政策 | 策略 | 输入、参数、状态和能力完整；修改产生独立候选 |
| 历史模拟账本与执行事实 | 回测 | 固定实验条件、撮合假设、完整性与未决项 |
| 本地实时模拟及柜台/实盘运行事实 | 实盘 | 模式、账户、执行归属、事件与订单核对；模拟和真实账本隔离 |
| 绩效、归因、验证结论与报告 | 评估 | 原始事实、计算口径、限制及报告状态；不能据此绕过真实准入 |
| 调度触发、节点与诊断 | 系统 | 业务权限及真实结果仍由所属业务确认；调度/日志不替代交易账本 |

### 运行模式的可观察区别

| 模式 | 时钟与订单去向 | 账户及成交依据 | 停止和继续 |
| --- | --- | --- | --- |
| 历史回测 | 固定历史事件；内部模拟，无柜台发送 | 固定初始条件及声明的历史模拟规则 | 每次试验独立；中断结果不得伪装完整，显式创建复核或重跑 |
| 本地实时模拟 | 真实实时事件；仅内部模拟 | 显式模拟账户起点及支持的撮合/费用规则 | 保留账本；连续性和状态可核对才允许明确继续，否则新实例 |
| 柜台仿真 | 实时输入；指定外部仿真柜台 | 仿真柜台的账户、订单与成交事实 | 独立仿真授权和风险；断线查询不重发，不等于实盘能力证明 |
| 实盘 | 实时输入；指定真实柜台账户 | 真实账户事实、必要记录、统一风险占用 | 账户与策略独立授权；正常跨日条件和故障恢复分别检查 |

本地模拟的初始资金可以由用户明确配置，不能伪装成真实账户资金；测试夹具不得进入正式行情展示。四种模式都不能靠切换标签共享授权或改写原有结果。

## 全量功能的验证组织

全部功能、页面、验收数量和关联旅程见[全量追踪](traceability.md)，该表从各条FR及UI/JRN引用生成，不能人工挑选少量新增功能代表完整覆盖。每项FR的AC逐一映射执行证据；UI交集只用于找到检查流程，不是已经通过的覆盖率。
