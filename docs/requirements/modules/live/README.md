# 实盘交易（Live Trading）

[返回上级](../../README.md) · [需求总纲](../../README.md) · [界面设计](../../common/ui-designs.md) · [跨模块流程](../../workflows/README.md)

开发前需求规格 · 2026-10-20。本文定义目标功能、业务约束、操作流程、界面字段及可观察完成条件。

**模块目标：** 明确账户、环境、策略和授权，管理真实运行、订单成交、账户政策与资金持仓，执行必要的准入及运行限制。

**职责边界：** 拥有真实账户事实、账户风险政策、统一准入与执行及运行限制；策略定义归策略，研究评价归评估，仿真或模拟不得混称实盘。

目标入口为**实盘 → 准备与运行 / 订单与成交 / 账户与核对**，具体视图见[界面设计总览](../../common/ui-designs.md#target-navigation)。一级和二级导航分别对应本模块与子模块。各页面的字段、动作和异常按所属子模块定义。

## 模块划分

第七个核心业务模块为**实盘交易（Live Trading）**，界面可简称 Live / 实盘。下设**实盘准备与运行管理、订单执行与成交管理、账户管理与交易核对**。它承接策略与评估结果，将明确授权的意图作用于真实账户；并不意味着上游模块的结果可以自动进入实盘。

| 子模块             | 核心问题                                             | 主要结果                                                   |
| ------------------ | ---------------------------------------------------- | ---------------------------------------------------------- |
| 实盘准备与运行管理 | 在哪个账户、什么范围内运行，当前是否真正运行或停止？ | 账户环境、固定方案、授权与启停、预警限制及恢复、行情上下文 |
| 订单执行与成交管理 | 意图是否被接纳、成交了多少、剩余订单怎样处理？       | 逐笔准入、在途占用、委托成交及未知结果核对                 |
| 账户管理与交易核对 | 实际资金和持仓是什么，记录能否与来源核对？           | 账户政策及生效、资金持仓、费用结算与核对证据               |

行情、自选、图表与订阅归入实盘准备中的交易上下文。行情采集与数据存储归数据；跨业务图表交互遵循通用规范。行情观察不要求用户先取得交易权限，不另设独立Visual模块。

## 实盘、仿真与本地模拟

| 环境                | 发生什么                                 | 不可混同的边界                                           |
| ------------------- | ---------------------------------------- | -------------------------------------------------------- |
| 实盘账户            | 指令发往真实交易账户，影响真实资金和持仓 | 要求明确授权、账户风险与统一执行路径                     |
| 仿真账户            | 指令发往明确标识的仿真柜台或测试账户     | 必须标仿真；它的授权、订单和业绩不能沿用或计入实盘       |
| 本地模拟 / 历史回测 | 在声明的模拟条件下生成模拟事实           | 无真实交易指令；必要风险不可缺，不以实盘授权作为运行前提 |

Live的业务主对象是真实账户。仿真准备可以复用账户和运行机制，但所有操作持续显示实际环境。账号名称、颜色或所在页面不足以证明环境，必须能核对连接目标与账户身份。切换环境不转移授权，不重定向既有订单，不把仿真结果当实盘业绩。

| 评估                           | 绩效、风险分析、稳健性、跨环境归因和报告         | 提供固定真实事实，审阅证据；评价通过不授予交易权限         |

| 系统                           | 连接机制、服务生命周期、任务和诊断               | 明确业务运行状态、授权和停止结果；窗口状态不代表交易状态   |

## 从准备到核对的闭环

确认环境和账户 → 读取固定策略与评估依据（手动交易核对完整意图） → 检查行情、资金、持仓、在途与风险 → 独立授权 → 明确启动或提交 → 观察订单与实际成交 → 核对账户 → 必要时独立暂停、撤单、平仓或停止 → 处理残余风险与结算差异。

只维护当前实例、账户和订单事实，不因用户切换页面改变归属。策略预算、实际资金、目标仓位、实际持仓和在途量分别表达。停止新意图不消灭之前发出的订单，连接恢复不构成重发授权。

## 界面上下文与操作边界

实盘/仿真文字、账户身份和关键状态在有交易后果的页面持续可见。行情查看、账户查询、授权、启动、提交和成交是不同状态，不能压缩成一个绿色“已连接”。界面使用Terminal的深色背景、青色焦点、紧凑表格和详情区；准备、运行及核对工作台按各页字段与状态规格操作。

订单类型、账户环境和柜台查询范围必须有明确能力依据。用户启用具体账户时核对GATE-TRADE所列来源信息；模拟结果不授予真实账户权限。

## 账户限制纳入现有业务操作

账户风险政策归账户管理与交易核对，逐笔准入与占用归订单执行与成交管理，预警/限制/恢复归实盘准备与运行管理。相关主题与案例在本模块唯一维护；不另设风险控制模块或独立风控中心。

账户配置、订单详情与运行详情相互跳转。风险限制覆盖手动和策略入口，策略预算不能替代账户政策，报告也不直接产生处置权限。共用定义见[共用交易约束](../../product.md#execution-risk-semantics)；配置、检查及运行限制分别有清晰状态与验收，每次发送都执行必要检查。

## 策略决策、证据与值守范围

自动策略以固定策略包声明的完整K线边界作决策。事件和定时触发只作为待消费输入，统一在不早于其实际可得时点的首个完整K线边界消费；同一边界按固定顺序合并处理，不能因事件到达额外产生一次盘中决策。一次边界先纳入旧订单在该边界已可得的执行与结算事实，再发布完整bar和可得事件形成状态截点，随后仅作一次策略决策，最后逐笔准入新意图；历史模拟中新订单与撤单最早作用后续bar。外部订单只按确切回报更新，不假定每个bar结束时均已终态。完整K线、边界归属与同刻顺序沿用策略/回测契约；手动下单与订单回报处理不受策略bar调度延迟。恢复时只依据当前有效输入形成新决策，不补发暂停期旧意图。

每次策略决策均形成最小证据，包含无新意图、目标零和被拒绝的决策。实际消费内容或可重取的不可变引用、可得时间、事件顺序、必要状态、固定逻辑/模型/政策及输出必须能关联；该证据独立于可选的全量实时行情留存。证据不可可靠保存时暂停新的策略决策发送，已有订单仍核对，查询与合规撤单按其条件保留。

产品支持有人值守的自动执行。值守人须能够持续观察应用内状态并使用已准备的券商官方处置渠道；不承诺离桌无人值守、自动接管或外部通知集成。关闭桌面窗口不会停止本地或远程服务，离开值守前应显式暂停新增、核对在途和持仓，并独立决定撤单或平仓。后台继续运行不等于仍满足值守条件。

关键存储失败、节点不可达或产品控制不可用时，值守人使用预先登记的券商官方客户端或官方人工渠道处置，记录账户、时间、动作和可取得的外部依据。产品不为应急绕过必要交易记录；恢复后先核对外部处置形成的订单/成交/持仓，再审查授权和执行归属，不能立即追逐旧目标补单。
