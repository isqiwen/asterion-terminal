# 需求评审、设计交接与验收规格

[需求总纲](README.md) · [范围与职责](product.md) · [设计总览](common/ui-designs.md) · [决定与配置登记](decisions.md) · [全量追踪](traceability.md)

开发前规格 · 2026-10-20。本文件规定需求文档应交付什么、如何评审、如何转化为设计和未来验收。业务目标、页面行为、方法定义、运行配置及外部能力要求各有明确归属。具体设计接受评审；账户拥有者的授权、风险限额和付费预算由使用者显式设置。

## 文档组成与完整范围

完整范围为七个核心业务模块、系统管理和通用规范，包含规则、模型、混合策略、多因子组合、情报、量化运行及恢复。模块README定义有限方法集合，子模块正文维护FR、输入字段、动作、异常、案例和AC。本文件不重复业务规则。

| 资料 | 回答的问题 | 交接要求 |
| --- | --- | --- |
| 产品定位与模块目录 | 为谁解决什么问题，范围多大 | 用户任务、边界、职责与优先级一致 |
| REQ / FR正文 | 软件应做什么 | 输入、触发、校验、结果、异常和验收可观察 |
| UI正文与目标设计图 | 页面长什么样，怎样操作 | 输入、只读信息、按钮分别定义；类型、单位、默认值、禁用条件和返回行为明确 |
| JRN业务旅程 | 用户怎样连续完成任务 | 前提、逐步操作、输出身份、异常、取消和完成条件闭合 |
| 决定与配置登记 | 哪些是设计选择，哪些由使用者填写 | 设计决定、运行配置、外部能力要求分列；每项链接唯一正文 |
| 全量追踪表 | 功能与验收如何关联 | 功能→主题/UI/AC可定位；显式旅程关联和仅共用页面的导航关系分开 |
| 共同对象和非功能规格 | 跨模块怎样一致，质量怎样衡量 | 字段语义、责任、状态、环境、负载、测量方式及阈值明确 |
| 图文阅读版与界面浏览 | 如何集中阅读和评审 | 从Markdown和SVG生成，能返回原文，不形成第二份规格 |

优先级用于说明安全必要性与业务依赖，不自动删减范围。范围外方法须明确不支持；范围内能力的输入不足须给出缺项和处理路径，不能用虚构结果、静默降级或未经声明的方法替代。

## 外部能力要求与运行配置

外部服务和设备有各自限制。以下表格定义接入必须满足的契约和未来核验方法，不指定某个账户或提供方已经满足条件。缺项只阻断依赖该项的业务，页面须说明原因和下一步。

| 约束编号 | 必须具备的资料或能力 | 验收方法 | 输入不满足时的产品行为 |
| --- | --- | --- | --- |
| GATE-DATA 来源与市场 | 提供方、授权用途、市场/品种、数据类型/频率/历史范围、交易日历、生效依据、费用配额和时点字段 | 用获授权样本核对查询/订阅、分页、修订、缺口、限额和合约规则；逐项对照能力清单 | 禁用依赖缺项的取数或执行，展示缺失字段、影响范围与配置入口 |
| GATE-INT 模型与材料 | 模型身份与位置、可处理材料、外发范围、输入上限、费用预算、超时/拒答和结构错误反馈 | 验证外发许可、超限、失败及证据核验；按事件族划分独立标注样本评价质量 | 允许保存材料与人工核验；缺发布条件不得自动发布，失败保留原因和消耗 |
| GATE-TRADE 柜台与账户 | 明确仿真/真实环境、账户身份、政策、订单能力、查询覆盖、日切/结算、紧急处置渠道 | 在隔离仿真环境核对部分成交、撤单、未知结果、跨日、归属冲突、记录失败；真实账户启用另需授权及账户事实核对 | 缺授权、风险或唯一执行归属不得发送；未知结果查询原请求，禁止自动重发 |
| GATE-RELEASE 安装与设备 | macOS Apple Silicon及Linux x86_64支持版本、产物身份、依赖、签名/校验、硬件和节点要求 | 两桌面安装/启动/卸载和资料保留、Linux节点运行、质量基线及完整性核对 | 不支持的环境明确拒绝或限制；保留原文件，不迁移、清空或伪装成功 |

必需运行配置包括：来源用途与预算、样本划分和验证计划、账户风险限额、运行模式与授权、调度时区及保留规则。字段应规定类型、单位、合法范围和缺失反馈；不得预填可交易限额、付费授权或实盘许可。配置记录应包含操作者、时间、对象、内容身份、作用范围和生效条件；秘密只保存安全引用或会话输入。

## 未来验收的层次与证据

| 层次 | 验收环境与动作 | 通过判据 |
| --- | --- | --- |
| 需求评审 | 逐条阅读规格；人工推演规则策略和多因子两条完整旅程 | 无未解释的冲突；字段、公式、状态、作用范围及异常都有明确含义 |
| 领域与接口 | 固定数值样本及隔离外部输入，检查账本、时点、状态和拒绝行为 | 每项FR及其AC有预期与观察结果；数值、单位、舍入及边界符合定义 |
| 页面与交互 | 中文/英文、键盘、窗口缩放，执行各UI的输入、提交、取消和恢复 | 字段错误定位准确；按钮前提明确；已保存事实、未保存草稿和未知结果可区分 |
| 跨模块旅程 | 根据42条JRN，从所列前提完成连续任务 | 每步输出可被下一步按身份引用；主路径与关键异常均满足完成条件 |
| 模拟与外部联调 | 本地实时模拟、外部柜台仿真分别执行；覆盖完整交易日及次日开市 | 时点、在途、账户、结算与模式隔离正确；故障注入仅在隔离环境执行 |
| 非功能与安装 | 两支持桌面及Linux节点，采用质量基线的设备、数据、负载和测量口径 | 每项NFR达到阈值；保留采样、分位数、失败/超时数和产物身份 |
| 使用者验收 | 依目标路径完成任务，审阅结果与明确限制 | 使用者确认具体范围、日期和保留项；严重业务错误不得作为一般备注放行 |

### 验收记录模板

每条验收记录应含：FR/AC或JRN步骤、构建与插件身份、平台和设备、脱敏来源/账户环境、固定输入与前提、时间、预期结果、观察结果、证据位置、通过/失败/受阻/未执行、缺陷和复验结果。数值用例附计算口径；NFR附负载和原始样本。一个用例可验证多项AC，但须分别列出判定，不能仅按共用UI推定覆盖。

- **阻断缺陷**：错误发单、越权、未知结果重发、账本或资料损坏、使用不可得信息却被当作严格历史验证。修复并复验前不得交付受影响范围。
- **严重缺陷**：核心旅程中断、关键字段或计算错误、必要异常路径缺失、质量基线不满足。须修复并复验。
- **一般缺陷**：不影响业务结果且存在明确可操作替代的呈现问题。保留项须由使用者明确接受，并记录范围和修复安排。

## 文档完成判据与变更

文档交接应同时满足：范围有限且责任清楚；每项FR有AC及UI去向；每项UI有入口、布局、输入、只读事实、操作、状态、返回方式和设计图；旅程输入输出闭合；决定各有处理方式；NFR可测；正文、图稿、公式与链接一致。设计评审通过后，未来软件验收按上述层次逐项执行。

修改需求须说明原因、内容与影响范围，同步FR/UI/JRN/AC、图稿、方法、外部能力和质量目标。业务配置改变不应反向修改需求含义；固定研究与运行对象按内容身份保留。历史由Git记录，正文只维护一套有效规格。

生成命令为 `pnpm run docs:requirements`，检查命令为 `pnpm run docs:requirements:check`。`requirements.html`、`prototype.html`、`decisions.md`和`traceability.md`均为派生文件；修订时编辑所属Markdown和SVG源文件。
