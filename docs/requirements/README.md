## 界面需求与设计

目标主导航依次为**数据、情报、分析、策略、回测、评估、实盘**，二级导航对应子模块；**系统管理**为底部辅助入口，任务、通知和连接状态为全局入口。延续已有视觉与控件，不保留旧六入口作为目标结构。

先查看[界面设计总览](common/ui-designs.md)：列出全部58项UI的承载形态、目标入口和主要布局，并进入所属模块查看逐页设计图、字段和操作规格。

UI设计在各子模块的界面条目内维护，必须包含入口、布局、字段、操作、状态、案例图和验收。统一遵守[UI设计内容与已有风格延续](common/interaction.md#ui-design-contract)，参考现有Terminal布局与公共控件；实际截图与新增设计稿明确区分。

## 编号和唯一归属

- 业务主题采用 `REQ-模块-子模块-序号`，例如 `REQ-DAT-ACQ-01` 表示数据/接入与采集的第一个主题。
- 功能采用 `FR-模块-子模块-主题序号-功能序号`；界面采用 `UI-模块-子模块-序号`。
- 验收附在主题、功能或界面编号后，使用 `-AC01` 等后缀；决定与配置记录采用 `DEC-模块-子模块-主题序号-事项序号`。
- 跨模块流程统一编号为 `JRN-001` 起，不强行归入一个模块。
- 编号按业务归属命名，目录顺序调整不改变需求编号；正文、图示与链接保持一致。只维护当前规格，不提供旧编号别名、旧文档入口或对照附录。

## 如何维护

当前共有7个核心业务模块（数据、情报、分析、策略、回测、评估、实盘交易）、1个系统支撑模块（系统管理），合计8个模块、23个业务子模块和3类通用规范，承载65个业务主题、304条功能、58项界面对应、42条流程及1002条分层验收。数量用于检查内容完整性，不代表实现完成。一级与二级导航分别对应模块与子模块；业务划分不决定插件、进程或数据库数量。

子模块内集中维护目标与职责、对象字段、正常与异常操作、案例及结果图、界面对应和验收；通用要求仅在通用规范维护，跨模块流程通过引用串联。基础资料属于数据管理与服务，质量和追溯贯穿数据三个子模块。核心提供机制，提供方、存储、策略和风险算法保持插件边界。

模块正文是需求和评审内容的唯一维护入口；评审意见、答复、确认状态和日期记录在对应需求、功能或验收条件旁。决定登记和全量追踪提供派生索引，阅读版由正文生成，界面浏览与实际界面说明保持同步。当前有截图不等于业务已通过验收，本次有限支持范围、字段与状态、非功能目标已有编制规格，细节签认和实际验收独立进行。过时内容直接更新或移除，历史由Git记录。

### 阅读版生成与校验

直接编辑本目录Markdown及其引用的SVG设计稿。运行 `pnpm run docs:requirements` 生成图文阅读版，再运行 `pnpm run docs:requirements:check` 检查唯一编号、链接、功能必要字段及阅读版覆盖。工具在 `scripts/requirements/`，依赖由项目pnpm锁定；生成器只写阅读版及两个派生索引，不写回模块正文或评审意见，不维护第二份功能目录内容源。

实际界面浏览 `prototype.html` 仍只说明现状截图与58项界面对应；目标操作规格在各子模块正文，本轮目标线框另明确标为设计稿。实际入口、截图或对应状态变化时须同步该浏览页，不能由目标设计自动推断已实现。

全包保留304条功能、58项界面、42条流程及1002条原有分层验收，补齐10项可测非功能规格、58项页面字段与状态约定、9张关键状态图、全量功能追踪及交付计划；未执行产品验收。
