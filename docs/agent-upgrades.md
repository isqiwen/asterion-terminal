# Agent 生命周期与自动升级

## 产品行为（2026-09-27 最新决定）

Terminal 启动自动准备同一发行包的本机组件。正常更新只是“正在准备工作台”的一部分，不展示 Agent 版本冲突、升级按钮或要求用户先手工停止后台服务。当前开发机旧服务/配置的明确清理是一次性操作，不是以后更新的实现方式。远端升级与本机升级共享事务语义，但远端涉及持续运行的交易与多客户端，必须按目标机器的维护策略调度，不能因为某个 Terminal 启动就更新所有远端。

升级保留节点身份、证书、服务配置、账本、研究任务和行情归档；只替换已校验的程序。凭据不放入更新记录。程序更新不能静默迁移数据格式、忽略未知协议或把旧服务故障当成空白新节点。

## 当前已经实现

- 启动入口先调用本机程序检查，对可更新/可恢复状态自动调用更新事务，然后重新检查程序一致性，成功后才启动行情与研究服务。不再要求用户点击“升级 Agent”。
- 更新事务使用独占 bootstrap 锁、源程序平台和摘要检查、已安装程序摘要复核、确切的 OS 服务定义和进程身份检查。
- 严格 Maintenance 操作只接受全部服务停止的节点；协调 Upgrade 操作另外负责持久化排空、恢复及幂等完成，不绕过严格维护保护。
- 替换阶段保留事务记录，可继续完成停止、发布、重启；健康探测成功后清除事务。故障不删除用户数据、不伪报更新成功。
- 当前协调协议支持只读行情服务和研究服务。Agent 在同一管理锁内持久化 `maintenance-plan.json`，保留原服务配置摘要和运行意愿，冻结部署/启停/上传和新任务派发；研究服务停止接收新提交，允许运行中工作提交结果。等待进程正常退出后，才能进入程序替换阶段。私有健康通道执行合作式停止，排空路径不销毁仍在运行的 ChildProcess 来强杀。
- 原运行意愿不改写为停止。新 Agent 在 ready 阶段不启动服务，接到同一操作的 resume 后才恢复原本运行的服务；通过业务健康检查后写入 complete。完成记录保留用于响应丢失后的幂等重试，后续新操作可替换它。Agent 在排空阶段重启时，先等待记录中的原进程退出，PID 复用按仍存活保守处理；意外中断任务仍沿用显式重试规则，不伪装成成功续算。
- Terminal 在维护计划通过校验后通过正常行情断开接口结束只读连接，再等待 Agent 合作式停止服务。活跃行情的内存登录态/事件流不保留，更新后需要重新登录行情；不持久化密码、不伪报无损续接。交易/策略尚无升级专用恢复契约，因此明确等待或拒绝，不强停。旧 Agent 不支持 `upgrade_protocol=1` 时明确拒绝，不自动降级为逐个停服务。

## 下一阶段的协调流程

更新编排归 `apps/clients/terminal/native/`，机器进程控制归 `apps/services/node-agent/`，通用锁、进程和文件发布机制归 Core kernel。不要在 React 内协调子进程或维护业务账本。

1. **检查发行材料**：使用发行清单的 release ID、平台、摘要及管理协议能力，区分产品版本、管理协议版本与持久化数据版本。当前 `0.1.0` 字符串不足以确认程序一致。
2. **提交维护计划**：Agent 在同一个写锁下记录更新操作 ID、目标摘要、实例 ID、服务列表与原期望运行状态；拒绝新的部署、任务派发和修改请求。状态查询继续可用。仅在 Terminal 查询一次服务列表后逐个停止存在竞态，不能作为实现。
3. **等待可恢复边界**：行情先提交录制游标，研究任务提交检查点或等待完成，策略与交易先停止接收新指令并确认账本提交。实盘未来需专门定义账户和未完成委托的维护策略，不能把普通进程重启当成交易安全。没有恢复契约的工作保持运行并推迟更新；UI 仅在确实需要用户决策时说明具体业务原因。
4. **停止和发布**：持久化每一步状态，校验 OS 所属身份后停旧进程，确认相关锁释放，再原子发布目标程序。不得同时启动新旧 Agent。升级期间 Terminal 退出不应丢失维护计划。
5. **健康与恢复**：验证新 Agent 的实际运行构建身份、管理协议和存储可读性；依原期望状态恢复服务，检查业务健康后解除维护。原先停用的服务不能被自动拉起；不得重发交易指令。
6. **失败继续**：可判定阶段按事务记录继续，不从头再次部署。未知提交结果先检查事实。数据格式不可逆变化不自动回滚旧程序；只有被发行清单证明可读同一数据且未修改格式时才允许程序回退。

## 管理协议边界

后续需提供独立、稳定的更新引导契约，包含协议能力范围、运行构建身份和维护状态。业务 Protobuf 扩展不能要求先成功调用新版业务命令才能更新 Agent。引导版本不支持时明确拒绝，不通过忽略未知字段、旧协议转发或临时兼容分支绕过。本次清除开发机旧版，不加入为该旧版定制的替换路径。

## 必须验收的故障场景

- 已是当前程序时不停止服务；两个 Terminal 同时启动只能产生一个更新事务。
- 有任务、策略或交易正在执行时不丢工作、不产生重复订单；等待维护边界期间拒绝新增变更。
- 在计划提交、排空、OS 停止、文件发布、重启、恢复服务各阶段杀进程后，下一次启动可继续同一操作。
- 摘要改变、服务身份不符、磁盘满、文件发布结果不确定、健康检查失败时保留数据及证据，且不显示工作台已就绪。
- macOS LaunchAgent、Linux systemd 用户服务与 Windows 计划任务分别做原生验收；Linux 容器测试不能替代三平台 OS 服务验收。

上述完整三平台故障矩阵、活跃行情恢复、交易/策略维护边界和独立稳定引导协议仍需补齐。当前实现不能宣称所有场景无感升级。

## 本轮验收（2026-09-28）

新增真实进程测试覆盖公开通道拒绝内部控制、冻结新任务、运行任务完成、排队任务保留、排空/就绪阶段 Agent 重启、原运行意愿保持、其他更新操作拒绝，以及完成响应丢失后重试。macOS 使用独立 launchd 节点实际更新不同摘要的 Agent，验证运行行情服务恢复、停用服务保持停用、停止/发布检查点恢复与数据保留；见 `build/upgrade-native-running.log`。

开发机旧版节点的一次性切换前，确认仅有未连接行情服务和空任务研究服务、无工作进程。保留节点身份、业务目录与原运行意愿，通过现有管理接口停止空闲服务、核对 launchd 身份后替换程序，再更新服务制品并恢复。旧程序和原配置保留于节点 `pre-coordination-backup/`，记录见 `build/local-coordination-switch.log`。此操作不进入产品升级路径，也不替代新协调协议的事务验收。

开发机切换到新协议后再次触发了正常自动升级，`maintenance-plan.json` 已到达 complete、程序摘要一致、无遗留程序更新事务，且两个原运行服务已恢复；见 `build/upgrade-local-automatic-verification.json`。同一调试二进制的临时原生桌面包已实际进入工作台。排空等待超过当前单次编排期限时保留计划，下一次启动/重试继续；此时未强停工作，也没有后台自动重放交易命令。

### 启动与重复请求复验（2026-09-28）

完整桌面验收发现：同摘要的更新请求仍会发起维护并重启 Agent；首个客户端完成后，第二个客户端重试原请求也可能失败。现已在 bootstrap 锁内确认目标摘要和更新记录：程序已一致且没有待恢复的发布记录时直接返回，不进入维护、不改变进程或服务运行意愿。存在 pending 文件时仍拒绝，保留原证据。并发争用锁的客户端可以在首个操作结束后安全重试原请求；没有加入自动重发业务命令。

独立 macOS launchd 验收覆盖同版本 Agent/业务进程 PID 不变、两个并发更新调用、完成后带原摘要重试、未完成发布文件拒绝与保留，以及既有停止/发布检查点恢复。日志 `build/acceptance-native-upgrade-fixed.log`；修复前复现见 `build/acceptance-upgrade-reproduction.log`。

同日追加 Release 验收：Apple Clang/macOS launchd 与 GCC/Linux systemd 用户服务均通过上述完整升级脚本，日志分别为 `build/macos-release-native-upgrade.log`、`build/linux-native-service-acceptance.log`。Linux 运行于隔离 OrbStack Ubuntu 24.04 x86_64，并通过真实 loopback SSH/SFTP、受限账户初始化、系统服务注册、mTLS 部署和重启恢复；没有验证远程 Agent 自身升级、Windows 计划任务或物理跨机网络。

高级设置的手动诊断入口现已使用同一协调语义：运行服务不再直接禁用更新/继续恢复按钮，界面不再要求先全部停止、完成后手工启动。Agent 根据实际维护能力决定等待或拒绝，成功后恢复原运行意愿。界面没有自动重发更新或交易命令。正常启动仍自动完成检查和协调，用户无需进入此高级入口。

启动页的最后一步使用最终完整快照检查行情与研究连接，不再读取较早启动调用的成功快照；标记 stale 的状态不能进入工作台。新增断连与陈旧快照场景，并验证重试可恢复；日志 `build/acceptance-startup-final-probe.log`。首次设置标记只有用户进入工作台时保存。

### 测试节点污染导致启动阻塞（2026-09-29）

开发机发现 Terminal API 测试的 `asterion-terminal-test-*` 临时模拟账户被登记到日常使用的 Agent；测试删除临时目录后，托管进程与运行意愿仍保留，触发交易服务不支持自动升级恢复边界的拒绝。这不是等待一段时间就会消失的活跃任务。CTest 原有隔离包装保留，测试二进制新增入口检查：必须由 `tests/isolated_node.py` 提供隔离节点目录及测试标记，直接运行拒绝执行，避免误用日常节点。

本次开发机恢复仅针对已核实的遗留测试实例：经 Agent 正式接口停用，未删除服务记录或用户账本。已安装 Agent 还会拒绝加载账本目录缺失的停用服务，因此为这条已停用的测试记录恢复空目录并写入退役说明；没有重建账本或恢复交易，不能将此一次性测试清理作为产品数据恢复方案。程序发布阶段曾因该目录缺失而启动失败；使用与事务目标摘要一致的程序材料完成恢复，再更新到当前构建。未绕过维护计划、摘要校验或交易恢复保护。

验证：无隔离环境直接运行测试返回 2；隔离 `terminal_api` CTest 通过。开发机实际升级及行情/研究连接结果记录于 `build/startup-orphan-recovery.log`。真实交易/策略服务的自动升级恢复契约仍未实现，不能将测试遗留清理称为已支持交易无感升级。

### 已连接行情阻塞启动修复（2026-09-30）

已连接的只读行情原先永远不能满足排空条件，启动页每次重试都会回到等待错误。Terminal 现先取得行情客户端，再提交 Agent 维护计划；只有计划通过验证才调用正常断开接口，随后继续原有合作式停止、程序发布和恢复流程。提前取得客户端避免未连接服务收到排空请求后退出的连接竞态。无需更新时仍直接返回，不断开行情；交易与策略的维护保护不变。

macOS 独立 launchd 验收现在从已连接的测试 CTP 行情开始，覆盖升级恢复、停用服务保持停用、并发与幂等重试、数据保留和停止检查点恢复，日志为 `build/startup-upgrade-connected.log`。5 项维护与程序更新回归通过，见 `build/startup-upgrade-regression.log`；桌面打包与制品校验见 `build/startup-upgrade-package.log`。开发机原 draining 事务通过修复后的正常启动流程恢复为 complete，实际 Electron 已进入工作台，见 `build/startup-upgrade-recovered.png`。行情凭据不持久化，更新后需重新登录；不能据此宣称活跃行情无损恢复。
