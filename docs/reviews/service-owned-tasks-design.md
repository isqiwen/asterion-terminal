# 按业务服务归属管理任务

日期：2026-10-21。状态：服务主动调度与实例并发控制已实现；Data／Research 任务归属拆分尚未切换。

本决定落实“先明确任务归属与 Core 公共机制，再判断是否合并进程”。本轮选择保持独立的
数据与研究进程，不将减少进程数作为收益。当前源码仍是 Data 与 Task 固定配对，下载、
回测及因子任务都由 Task 保存；以下目标不能作为已经交付的功能说明。

本文件仅展开任务归属切换；全产品边界与工程组织以[需求驱动目标架构](architecture-design-review.md)为准。
Research承载分析、策略、回测、评估，Intelligence拥有情报任务。执行采用所属服务的有界线程池
与异步I/O。当前Task已移除worker机制，`task_concurrency`默认1、最多2；任务归属拆分仍待实施。

## 问题与选择

当前 Task 并非仅用于启动进程：它拥有任务账本、执行尝试、取消确认、计算结果以及分钟
下载的持久发布决定。Data 拥有授权、历史版本与实际数据发布。下载跨两个业务状态拥有者
完成，研究任务与下载任务又共同存在于 Task 账本中。

| 方案 | 影响 | 决定 |
| --- | --- | --- |
| 保留一个通用任务服务 | 维持现有实现，但下载状态与数据发布继续跨服务协调 | 不作为目标 |
| 数据服务管理下载，研究服务管理计算 | 任务跟随业务所有者；公共机制通过 Core 复用；仍为两个业务进程 | 采用 |
| 将数据和研究合成一个服务 | 少一个常驻进程，但数据访问与研究管理共用故障和升级边界 | 本次不采用 |

原任务服务在职责拆分后成为研究服务，不同时保留通用任务服务和研究服务。

## 唯一所有者

| 对象 | 所有者 | 负责的决定 |
| --- | --- | --- |
| 分钟下载、全市场更新 | 数据服务 | 输入与来源授权、队列、执行尝试、进度、取消、重试、数据发布与任务完成 |
| 回测、因子分析 | 研究服务 | 固定输入、队列、执行尝试、进度、取消、重试、结果验收与查询 |
| 交易和行情内部工作 | 原业务服务 | 继续使用账户、订单、连接与订阅模型，不强制转换为通用任务 |
| 服务进程 | Agent | 本机进程启动、停止、回收和存活进程观察 |
| 节点登记与管理连接 | Manager | 状态汇总、端点发现和管理指令，不经过业务载荷 |
| 任务中心 | Terminal | 查询并展示各服务任务；操作发给任务拥有者，不另存权威任务账本 |

任务身份必须包含所属节点、服务实例与该服务内的任务 ID。两个服务允许相同任务 ID；
取消、重试、详情和结果查询不能仅凭任务 ID 猜测目标。执行尝试身份继续阻止旧尝试
报告修改后续尝试，不额外新增摘要、代次门槛或全局任务登记服务。

## Core 复用范围

已有 `ThreadPool`、`PolledTask`、`RpcHost`、`durable_file` 和有界队列应直接复用。
Core 不新增常驻进程，不持有所有服务共享的数据库，不读取具体服务目录。

- `foundation` 保留与业务无关的基础类型和队列。
- `kernel` 提供执行、取消、文件持久化及异步完成交接机制；不认识下载、回测或因子类型。
- 确认双方需要的任务身份、执行尝试和公共状态语义，可归 `domain`；网络 Protobuf 与序列化
  映射仍归 `protocol`，Core 不反向依赖协议生成代码。
- SQLite 实现留在存储插件。是否提取任务账本接口由两个实际调用方需要决定，不预设一个
  全功能任务框架，不把现有混合业务的 `Store` 或 `TaskHost` 整体移入 Core。
- 公共代码可以处理尝试状态和异步持久化交接；来源授权、固定计算输入、数据发布、结果
  验收和是否允许重试，由相应业务服务决定。

公共机制只保存调用方实例自己的状态。服务分别持有对象与存储连接；共享实现不意味着
共享可变状态，也不要求所有服务使用一套包含全部业务分支的状态机。

## 执行与资源边界

任务在所属服务进程内执行。服务状态所有者持久接纳并决定并发，准备固定输入后提交给有界
线程池；执行线程独占算法状态，通过原子进度和一次结果交付回到状态所有者。
Agent只管理业务服务进程，不参与任务线程、队列、尝试和结果。没有任务进程启动、退出确认、
领取RPC或心跳租约。取消协作停止，服务重启后的中断工作须显式重试。

当前Task已改为此执行方式，`task_concurrency`默认1、允许1–2。Data/Research职责拆分
仍待实施；拆分后分别拥有策略，Research四模块共用一份实例上限。

## 数据发布和失败语义

分钟下载的发布决定与任务状态都归 Data。不能在数据尚未公开时先宣告任务成功，也不能因
公开后回复丢失再次执行下载。文件块和元数据的现有持久发布边界继续保留；只消除没有独立
所有者需要的跨服务发布握手，不假设移动到一个进程就获得文件系统与数据库的共同事务。

全市场更新继续逐分区公开：取消或失败不撤销已经发布的分区，任务结果报告实际完成范围。
研究计算线程 继续直接读取 Data 的固定版本；Research 保存计算定义和结果，不复制整个数据
仓库，不因 Data 离线自动改读其他仓库。

取消请求只有在执行方确认后才是取消完成。进程丢失不能冒充成功；新一轮重试由用户明确
发起。关闭安装版 Terminal 不停止已接纳工作；服务重启从自己持久状态恢复可解释的任务
状态，不自动重发交易指令。

## 持久化与配置

默认配置继续由仓库根 `config/` 部署，启动只读。任务、执行尝试、结果和服务部署是所属
服务的持久状态，不生成到策略配置中，不由安装器另建任务清单。

现有任务账本包含混合业务记录。本项目未发布，不承诺旧开发格式兼容；实现切换不能静默
拆分、迁移或删除现有文件，也不能把缺少旧文件当成空仓库覆盖。若当前契约无法读取已有
资料，应明确报告目录和原因。新实例使用明确选择的空目录；不新增旧服务兼容运行路径。
当前阶段不执行任何运行目录或用户资料修改。

## 实施顺序与验证

1. 先固定任务拥有者和请求／回复契约，再从现有实现提取双方需要的最小 Core 机制。
2. 在同一条业务链路中完成 Data 的下载任务、内部执行结果及发布闭环；同步 Research 的任务
   范围和服务主动启动请求，不让两个进程同时成为同一任务的拥有者。
3. 同步 Terminal 任务作用域、聚合展示、取消、重试和结果读取，以及部署、默认单机启动和命名。
4. 删除原通用任务服务的多余接口、固定配对耦合与对应旧测试；更新现行文档和打包资源。

验证以真实行为为主：本机下载与研究分别完成；同 ID 跨服务操作正确；Data／Research
同时排队遵循各自并发上限且互不阻塞；取消、执行失败、服务重启及数据发布边界不丢失或误报任务；
关闭并重开 Terminal 仍能观察工作；已有文件不被迁移或覆盖。前端用组件测试验证路由，
业务状态在 C++／隔离进程测试中验证，不添加构建架构守卫或规则扫描。

本轮已实现当前 Task 服务的实例并发控制和主动启动请求，删除 Agent 的节点额度及队列轮询机制；未改变混合任务
账本、Data／Task 固定配对和 Terminal 单任务来源。后续完成任务归属拆分后，才能将这些
现行架构说明替换为 Data／Research 契约。
