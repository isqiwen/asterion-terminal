## 已确认问题

### R1 · P2：公开接口可以直接领取任务，绕开 Agent 的执行准入

代码：[task_host.cpp](../../apps/services/task-service/task_host.cpp) 594–638、719–720、782–803；
[task_store.cpp](../../apps/services/task-service/task_store.cpp) 1576–1589。

`dispatch` 明确要求私有 worker 通道，但 `claim` 没有相同限制。
公开接口能够取得有效执行令牌，随后也能调用进度、完成和失败接口。
`Store::claim` 检查任务处于排队状态和尝试次数，却没有 Agent 派发或容量批准这一前提。
正常路径中的两个 worker 上限和 Data 就绪检查都在 dispatch，直接 claim 不经过它们。

**复现：**在独立临时任务库创建三个排队回测任务，只启动 Task 服务，
不运行 Agent 或 Data。通过公开 client socket 逐个 claim，三个全部返回有效 attempt。
该测试没有启动三个计算进程，因此直接证据是“越过准入创建三个运行尝试”，
不据此宣称已实测节点 CPU/内存超额。

影响：任务列表可以出现 Agent 未拥有的运行尝试，失去“执行由 Agent 管理”的保证；
公开请求也能占用原本为 worker 保留的输入/完成复核名额。
本机公开 socket 与 TLS listener 均进入 `Lane::client`；本轮实测前者，
TLS 分支的结论来自共用代码。需要既有本机权限或已认证远程身份，不是匿名漏洞。

**建议：**在 TaskHost 的通道边界统一限制 claim/progress/finish/fail/cancel_ack，
使它们仅走私有 worker 通道，连同已有 dispatch 规则一起定义清楚；
公开接口保留用户提交、查询、取消、显式重试及元数据编辑。
同步更新仍把 worker 接到公开 endpoint 的进程测试。
无需增加另一套任务调度器或通用权限框架；同 OS 用户的可信代码仍不是沙箱边界。

验收：公开通道拒绝领取和执行回报；私有通道完整 worker 流程仍通过；
Agent 容量、取消、恢复和升级测试不退化。

### R2 · P2：数据表刷新回执没有与固定任务目标核对

代码：[task_store.cpp](../../apps/services/task-service/task_store.cpp) 1636–1672、1683–1699、1098–1100；
[data.cpp](../../protocol/src/data.cpp) 537–564。

完成 TABLE_UPDATE 时，只调用 `decode_table_update_result` 验证结果自身可以解码，
没有把 `refreshed_revision` 或 `refresh_observation` 与任务的固定 TableUpdate、
实例身份及尝试身份比较。回测/因子验收已经执行输入与结果之间的校验，
数据表结果却止于结果自身格式。保存结果时生成的摘要只能证明后续字节未变，
不能证明回执属于本次请求。

**复现：**任务固定刷新 `futures.daily / SHFE / 2024-03-01`，提交的回执却为
`futures.daily / DCE / 2024-04-01`，来源和 provider artifact 也不同。
完成接口接受它并置为 SUCCEEDED，随后 `verified_result` 仍返回这份错配回执。

影响：任务页及后续研究证据可能把另一个分区、日期或来源的回执归到本次刷新。
本探针构造了错误 worker 结果，没有改写实际 Data 分区，不证明生产 worker
当前会主动生成这类错配；它证明任务结果的验收边界缺少已经可核对的约束。

**建议：**为 TableUpdate 结果提供接收固定定义和尝试身份的类型化校验，
核对显式刷新目标、来源、artifact，以及存在 observation 时的任务/实例/尝试归属；
统一用于完成验收和结果读取。正确保留“无数据、被拒绝、已有相同内容”的不同结果，
普通全市场更新也不能强制套用单分区刷新条件。
读取已保存结果仍应可以离线完成，不需要重新下载、运行算法或每次访问 Data。

验收：错分区/日期或错尝试的回执被拒绝；正常修订、未变化和无数据结果保持可用；
拒绝时不记录成功、不改变已有数据。

### R3 · P2：接纳等待的 10 秒期限无法终止正在等待数据库的请求

代码：[task_host.cpp](../../apps/services/task-service/task_host.cpp) 69–71、115–120、197–208、724–727、860–861；
[rpc_host.cpp](../../core/src/kernel/rpc_host.cpp) 146–179。

`Call::admitted` 能检查 deadline，但 `wait_for_store` 的等待条件只有写入完成或降级，
不含时间。handle 必须先从 `ready` 返回，才能再次调用 admitted。
RPC 层对于 pending handler 也不执行普通收发超时。因此日志提交一直未完成时，
新列表、冷任务读取或同任务操作会持续占据请求槽，直到写入返回才报告早已发生的超时。

**复现：**使用仓库已有的 SQLite 提交暂停钩子，暂停一个取消操作的 COMMIT，
随后发起 list。持续推进真实 TaskHost 的状态循环 11 秒，list 仍没有回复；
释放提交后立即收到 `task request admission timed out`。
这是隔离故障注入，不是对当前机器磁盘性能的测量。

影响：慢盘/停滞日志写入期间，配置的接纳期限不能释放尚未接纳的请求；
客户端即使已经超时，服务端仍保留槽位。多个此类请求可以耗尽业务通道容量，
而独立健康心跳仍可能正常。没有证据表明该现象会破坏已经确认的持久状态。

**建议：**让“尚未接纳的等待”同时观察 deadline，并在到期后安全退出，
不执行数据库读取或新变更。已经接纳的持久写、以及文件线程仍引用协程局部对象的操作，
继续保留到其工作结束；不要把统一网络超时套到所有 pending handler 上，
否则会破坏现有的持久性或对象生命周期保证。这个区别应在等待接口中明确表达。

验收：暂停 COMMIT 时，新查询在预算内得到错误并释放槽位；
原写入释放后只确认一次，活动状态、取消结果和恢复记录保持一致。

## 值得保留的架构与实现

| 边界 | 当前实现与判断 |
| --- | --- |
| Task / Agent | Task 决定任务顺序和状态，Agent 管进程及节点资源。正常派发路径职责清晰；R1 是入口约束未闭合。 |
| Task / Data | Task 保管输入、尝试和计算结果；Data 拥有历史分区、版本、授权及供应商预算。固定配对避免任意跨节点协调。 |
| Task / worker | Task 不运行回测/因子引擎，worker 每次执行一个尝试；计算崩溃不会在 Task 的状态线程内传播。链接检查未发现两个引擎的 run 符号。 |
| 状态 / 持久化 | TaskHost 主线程裁决状态；Change 提前构造变更，单日志线程持久化，confirm 后公开内存状态。当前活动记录与 SQLite 投影不是两个可独立写入的业务拥有者。 |
| 慢文件操作 | 输入读取、结果验证和文件落盘交给固定池；交回状态侧后重新核对令牌和取消状态。不能用“文件写完了”代替“任务已成功”。 |
| 尝试与取消 | retry 保留原固定输入并创建新尝试；旧令牌被拒绝。运行中任务重启后中断，需要显式重试。 |
| 分钟下载发布 | Task 持久记录 PUBLISHING 后，Data 才公开对应候选；发布决定可在 worker 消失后继续确认同一版本。它不是跨服务原子事务，也不重新下载。 |
| 全市场表更新 | Data 逐分区入库，取消不撤回已入库分区；这是不同于分钟版本发布的明确业务语义，不能强行统一为同一事务。 |
| 恢复 | 检查输入/结果摘要、事件序列与索引；不按新算法重写旧任务。已完成结果的格式不受支持时拒绝单项读取，保留文件。 |
| 容量 | 活动任务 1,000，历史分页 200；正常 Agent 路径节点 worker 上限 2，另受 CPU/内存/磁盘预算约束。连接、文件池和复核名额有界。 |

这套骨架无需为了修复上述问题引入消息队列、通用工作流引擎、跨节点抢占、
自动任务重跑，或把 Task 与 Data 合并成一个更大的服务。

## 结构性债务与尚未验证的风险

这些项目与上面的三个复现缺陷分开，不宣称已经造成运行故障。

1. **业务校验和实验构造过多集中在两个大类。** TaskHost 912 行，其中约 280 行用于
   回测构造、复用和因子提交；Store 1,808 行还承担回测领域结果验证、摘要生成、
   存储格式和恢复。问题在职责耦合，不是行数本身。应把具体业务的输入/结果校验
   放回类型化的业务协议边界，让 Host 保留异步编排，让 Store 保留状态与持久记录。
   无需为当前四类任务创建通用注册表或插件化任务框架。

2. **JSON 表示进入了服务内部业务判断。** `submit_factor` 在 563–566 行先把已验证的
   Protobuf 结果转为界面使用的 JSON，再读取 `experiment` 构造复用请求；
   这使服务端依赖展示字段。Store 的 manifest/state event 也使用 JSON，
   与仓库“JSON 限于协议边界与 UI”的现行规则存在张力。
   优先用固定类型输入完成因子派生校验，消除展示契约依赖。
   持久格式改变必须单独设计版本拒绝和用户数据保留，不能在一次清理中自动迁移旧库。

3. **恢复工作量仍随历史增长。** 当前启动先做只读预检，再完整复验；对所有输入、
   已完成结果和事件重放做验证。事件分段保留有界内存，但不能保证启动耗时有界。
   `read_task` 对包含该任务的段逐段扫描，在交错事件较多时也有额外成本。
   本轮测试覆盖了大输入恢复，没有进行多年任务库、冷缓存或慢盘的恢复时间实验。
   应先给出实际数据规模和可接受恢复时间再测量，不据此直接引入快照/恢复捷径。

4. **部分性能工作仍在状态线程。** 回测合约组织、部分因子序列组装、列表查询与回复
   序列化仍有同步工作。现有最大输入、并发控制测试通过，不构成任意负载下的延迟保证。
   在出现真实延迟证据前，不建议继续增加线程或拆出新的常驻服务。

## 获批重构设计（2026-10-15）

用户已批准按本报告整改。比较了“增加通用任务类型/准入框架”和“沿现有边界补齐约束、提取业务协议函数”两种方案，选择后者：

- TaskHost 继续拥有状态线程、异步编排与等待生命周期；所有执行操作统一要求私有 worker 通道。
- Store 继续拥有固定输入、状态变更和持久确认。回测结果校验移到业务协议层；表更新结果用固定输入和尝试身份校验，完成与读取共用。
- 初次接纳等待观察原有 10 秒期限；已接纳的文件和持久写继续等待完成，避免销毁后台工作引用的对象。
- 因子复用通过类型化参数构造，与界面 JSON 入口共享派生规则，移除 Host 对展示 JSON 的依赖。
- 不改变持久格式、引擎算法、服务拓扑和任务重试语义；不迁移或修改真实任务库。正式测试覆盖已复现边界和正常工作流，替代临时探针作为回归入口。

## 获批重构实现

- **R1 已修复。** TaskHost 在输入/结果复核和状态访问之前统一检查六种执行操作的通道，
  公开 Unix/TLS 入口返回 `permission_denied`。同步任务及数据模块进程测试的私有 worker endpoint；
  Agent 仍拥有容量与进程生命周期，未增加另一个调度或权限框架。
- **R2 已修复。** `protocol::validate_table_update_result` 接收固定 TableUpdate、DownloadIdentity 和结果。
  Store 完成验收与离线读取共用该函数，核对分区、来源、快照及 observation 归属。
  新入库修订核对当前 artifact；未变化修订允许保留首次入库的 artifact，
  本次 observation 则必须使用当前 artifact。普通更新、无数据和可选 observation 的语义保留。
  已保存但错配的结果可以继续列出，拒绝读取其证据，不改写文件或破坏整个库的恢复。
- **R3 已修复。** 初次 `ready` 把接纳 deadline 传入数据库等待条件；到期释放尚未接纳的请求。
  已接纳工作仍使用不截断的等待，保持文件线程引用与持久写确认的生命周期。
  暂停 COMMIT 的回归同时验证查询按时失败、原取消完成与关闭后恢复。
- 回测输入/结果关系校验完整提取到 `protocol/src/backtest_result.cpp`，Store 保留类型分派。
  核对提取前后的校验函数体，仅输入参数改为 BacktestInput，算法与引擎标识未变。
- 因子派生改用固定输入的 TaskExecution 参数；类型化入口与 JSON 边界适配器共享派生规则。
  Host 不再为业务判断构造完整结果展示 JSON。固定/新快照、窗口约束、流动性规则与分组顺序保持一致。
- TaskHost 构建为服务与进程内回归共同链接的静态目标，仍由单独服务进程运行；
  链接检查没有发现回测或因子引擎的执行入口。

本轮不重写持久 JSON 格式，不新增任务类型框架；大库恢复耗时和未实测负载下的性能边界仍是
原报告中的开放事项，不以本轮回归代替规模测量。
