# 实盘观察出口类型化

## 基线与设计

2026-10-16，按用户“继续推进框架的优化”要求，在主 checkout `main` 的 `723f418`
及前一轮未提交的[类型化接口修改](typed-boundaries-2026-10-16.md)上继续工作。
复核原架构设计、实施记录与审计进度后，选择收敛已明确存在的实盘观察中转，不扩展插件框架。

根问题：柜台已返回类型化 `BrokerSnapshot`，账户政策也已有 `Decimal` 和合约类型，
但 `LiveAccountState` 将这些数据转换为 JSON；账户线程通过 `future<Json>` 交给服务，
服务再次读取字符串字段并解析金额，构造 `LiveSnapshot`。策略定义也经过 Protobuf → JSON
→ Protobuf。这些转换没有独立业务责任，增加接口错配与数值编解码的维护成本。

比较两种可行设计：

- 新建实盘观察 DTO，再在服务中转成 Protobuf：适合有独立领域消费者的场景，但当前只用于
  账户服务回复，会多维护一套已有协议同构的数据结构。
- 账户观察出口直接构造已有 `protocol::v1::LiveSnapshot`：服务层已经依赖协议，拥有
  所需的账户事实与政策；选择这一方案。Core 的柜台接口继续返回类型化领域状态，不依赖协议。

状态仍只归账户线程所有。读取取得脱离后续修改的协议值，经 future 交给 I/O 层发送，
Terminal 收到后才转换为 UI JSON。构造失败仍通过 future 异常与现有 `ErrorCode` 回复，
不返回空快照、不重试交易。授权、断线不重发、持久日志和发送许可不作改变。

## 实现

- `LiveAccountState::snapshot()` 与 `LiveSession::snapshot()` 返回当前 `LiveSnapshot`。
  直接编码政策、合约、资金、持仓、委托、成交、费率、未知委托、授权、策略和日志容量。
  金额直接写入固定精度 `Decimal.units`；策略定义直接复制已有协议值。
- 交易服务 I/O 接收类型化 future，直接放入回复。删除 `encode_live_snapshot(Json)` 的
  声明与完整实现，不留下兼容入口。
- 保留 `decode_live_snapshot` 作为 Terminal 的协议验证和展示出口；配置、命令与日志
  编解码不在本轮重写范围。不能据此宣称实盘服务所有 JSON 都已清除。
- 既有账户行为测试在测试驱动中调用实际展示解码器，覆盖服务观察到 UI 的契约。
  删除只验证旧 JSON 编码器的合成往返样例，改为真实账户加测试 CTP SDK 的协议快照测试：
  固定精度、未连接时字段缺省、授权撤销后的快照独立性、序列化与非法协议数据拒绝。
