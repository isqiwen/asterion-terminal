### R1 撤权被 Terminal 的普通命令互斥挡住

位置：`apps/clients/terminal/plugins/trading/LivePanel.tsx:582`、`src/App.tsx:200`、`native/commands_live.cpp:153`、`native/application_impl.hpp:146`；服务端对照 `apps/services/trading/account_loop.cpp:392`。

界面的撤权按钮使用全窗口 `busy`，因此费率查询、报单等尚未完成时不能点击。即便绕过按钮直接调用 Native，`live.act` 只让 `cancel` 和 `strategy_stop` 走并行控制入口；`live_revoke` 仍进入 `with_live_account`，同一账户忙时立即以 `conflict` 拒绝。`live.disconnect` 也在普通互斥入口内。

交易服务本身已经正确实现：撤权在接纳时使发送许可失效，后续再完成持久记录。问题在于 Terminal 不让该请求到达这个边界。用户最需要中止新增执行的时刻，恰好可能有慢报价查询、SDK 操作或持久提交在途。

最小修正是让撤权作为明确的账户控制请求穿过 UI 和 Native，在账户服务排序；不需要取消普通命令的全部互斥，也不应由 UI 自行宣告撤权成功。保留“已经消费的发送许可不能撤回、已有委托不会自动撤销”的现行语义。

同一全局状态还在 `src/App.tsx:167` 暂停快照轮询，使慢命令影响整个窗口的账户和行情观察。普通操作的防重复、紧急控制的接纳和状态观察应分别处理，继续复用现有修订号与在途轮询控制即可。

验证应保护同一账户的慢操作与撤权竞争，并增加一个 `busy=true` 时仍可触发撤权的组件用例。现有 `TerminalLive.DelayedAccountDoesNotBlockOtherAccountControlsOrSnapshots` 验证的是另一账户，不能覆盖这一缺口。

### R2 实盘策略把预热过程中的旧信号当作当前执行目标

位置：`apps/services/trading/strategy_host.cpp:70`、`live_session.cpp:499`、`live_session.cpp:513`、`live_session.cpp:610`、`account_loop.cpp:171`、`account_loop.cpp:242`。

启动策略时，StrategyHost 读取当日已有分钟线，逐根更新算法并逐根向账户发布目标。账户循环每消费一个事件就推进策略执行；它没有“这批历史数据尚未追到最新完成 K 线”的边界。`place_target` 一开始复制当时的 `run.bar`，随后异步查询报价和提交，之后更晚的预热事件不会撤销这个已开始的旧目标。

隔离复现使用当日已完成收盘价 `3500 → 3501 → 3499 → 3498`，末尾另有形成中的 K 线，规则为 SMA(1,2)、只做多。最新目标应为空仓；观察到策略快照已经是 `bars=4, target=0`，测试柜台却有来自早期信号的 `buy open 1 @ 3501` 成交。保护“预热旧目标不产生委托”的临时 GoogleTest 按预期失败。该复现只连接测试 SDK，不是真实柜台成交。

这不是授权或风控被绕过：旧目标仍通过统一执行链。根因是算法状态推进与可执行目标发布没有分开，允许一个已过时的合法信号产生外部副作用。

最小设计是按一次读取批次推进全部算法状态，只将追到最新完成 K 线后的目标发布给账户；明确初始预热、积压追赶和新实时数据的发布边界。相比逐根事件后再增加多处取消或检查，这能从源头减少过时目标进入账户。测试需覆盖中途曾做多、最新已经空仓的启动序列，以及正常新增 K 线仍能下单。此项改变交易命令语义，修复时必须更新交易日志引擎标识。

### R3 行情重启检测只活在一次轮询里

位置：`apps/services/trading/strategy_host.cpp:63`。

代码用同交易日的 `first_observation_ms` 变化推导局部变量 `restarted`，随即保存新的 `first`；但只有进入“新增完整 K 线”的循环时才处理 `restarted`。

实际可达顺序是：已有策略状态；行情服务重启；首次回复只有开始观察的那根或仍形成中的 K 线；这轮没有符合条件的 bar，重启信号未被处理；下一次回复有完整 K 线时 `first` 已相同，`restarted` 变回 false。策略便使用重启前的算法状态继续处理重启后的行情。

隔离探针观测为 `before=2, after=4, failures=0`，并继续产出 `-1`、`+1` 目标。这与现行交易文档所规定的行情重启/观察中断结束运行不一致。新行情服务自身的 `interrupted` 无法证明旧进程与新进程之间的连续性。

应把已观察到的连续性破坏保留到明确裁决，而不是下一次轮询自动遗忘。如果保持“收盘后没有后续 K 线不算中断”的语义，可延迟裁决到新增 bar，但不能丢失证据。无需补造行情、自动重新预热或自动恢复交易。增加“重启首包尚无完整 bar”的一个回归即可覆盖根因。

### R4 均线比较把统计中间量限制在账本金额范围内

位置：`plugins/strategy/cta/strategy.cpp:54`，参数范围在 `protocol/src/trading.cpp:200`。

均线交叉通过 `fast_sum * slow` 与 `slow_sum * fast` 比较均值，两个乘积仍存入八位小数的 int64 `Decimal`。参数允许 `0 < fast < slow <= 10000`，但比较量的量级是“价格 × fast × slow”，远大于单个价格或账户资金。

合法参数 `fast=500, slow=1000`、恒定价格 `200000`，在第 462 根 K 线即抛 `decimal overflow`，尚未完成慢线预热。此时均线值本身完全在范围内；这是中间表示不合适，不是市场数据非法。实盘和回测使用同一策略实现，因此都受影响。

应采用足够宽的整数累计与交叉比较，保持精确比较；账本金额、价格、委托仍使用 Decimal。仅把乘法移到预热完成后不能解决最终溢出；缩小全局 Decimal 精度或改动账本类型也没有必要。用高价格和中等窗口的一个成功场景保护即可。

### R5 分时图没有把行情来源纳入请求身份

位置：`apps/clients/terminal/plugins/futures-market/QuotePane.tsx:43`、`QuotePane.tsx:311`、`native/commands_market.cpp:108`。

`useIntraday` 的 effect 和组件 key 仅取交易所与合约。设置窗口切换行情服务后，如果两个服务都订阅同一合约，主窗口组件仍存续，旧序列不被清空。每三秒的查询也允许重叠，完成时只核对合约，不核对服务身份或请求顺序。

Native 为查询保留原 `reader` 的生命周期是正确的，但查询完成后直接把原服务的 `intraday` 加入当前已发布快照，没有检查当前 `market` 是否仍为该 reader。因此，一个慢的旧源查询可在切换后返回，并覆盖新源已经显示的序列。

这是观测来源混淆，不代表服务端账本或策略数据被改写。应让读模型携带来源/观测代次，UI 按该身份清空或隔离缓存并拒绝迟到结果；边界上已不适用的读取也可明确拒绝。沿用现有 Tick 图的来源身份思路即可，无需通用缓存框架。

隔离 jsdom 组件探针已复现：A 查询尚未返回时切到同合约的 B，没有触发新查询；A 随后返回，B 上下文显示 A 的观测时间，直到三秒后的 B 回复才替换。探针的一项断言通过，表示成功确认当前缺陷，不表示该问题已修复。后续查询失败时，已有序列的错误也可能不显示，使旧图保留更久。

### R6 节点身份到期后没有现成的换证闭环

位置：`apps/clients/terminal/native/node_identity.cpp:24`、`node_identity.cpp:70`、`node_enrollment.cpp:506`、`node_enrollment.cpp:576`。

CA、服务端、管理员和业务客户端证书都只有 365 天有效期，CA 私钥仅在内存中存在。到期时 TLS 拒绝新连接是正确行为，但现有注册流程不能为原节点换一套新身份：同名本地目录只接受完全一致的登记并复用旧证书；只有目录不存在时生成证书；远端发布拒绝替换摘要不同的证书或安装记录。

公开命令中没有续期/替换身份入口；程序升级保留原身份，不能解决证书到期。代码也未提供原节点密钥丢失或泄露后的显式身份替换流程。没有在本轮推进系统时钟或操作真实远端；结论来自完整注册路径和调用点检索。

[原设计](architecture-design-review.md)已要求身份更新保留业务数据，[实施清单 M](architecture-implementation.md)却写为完成，当前证据不足以支持该完成声明。这是确定的功能与验收缺口，不能靠删除登记、换节点名称或手工复制账本充当产品流程。

最小方案是明确停机窗口下的 SSH 身份替换事务，保留原服务/账户/Data/Task 目录与身份，并验证中途失败、重新连接和业务引用完整性。没有当前需要建设在线 CA、自动续期平台或兼容旧身份协议。

### R7 常驻进程准入不保证任务有执行资源

位置：`apps/services/node-agent/resource_budget.hpp:39`、`main.cpp:327`、`main.cpp:538`、`main.cpp:727`；配对部署在 `apps/clients/terminal/native/commands_node.cpp:29`。

资源模型对每个服务分别准入，不保留 worker 的最小执行容量。以 10 CPU、足够内存的本机节点为例：文件池大小为 2，总 I/O 额度为 10；Data 占 3、Task 占 3、Market 占 1。再启动第二组的 Data 后占用正好为 10，第二个 Task 等待容量，已有 Task 的所有 worker 名额也变成 0。

即便当时没有任何 worker，这个状态也能成立；常驻进程不会自行释放额度，等待无法靠“任务做完”自然解除，必须显式停止服务。新增一组服务于是可能使原来健康的一组任务停止推进。容量不足排队本身是现行明确策略，这里的缺口是服务配对和可执行性未一起进入准入决策。

此项按静态可达的活性风险处理，不声称本轮复现了整个真实节点。`audit-progress.md` 的既有真实数据记录已出现新增一组后原任务等待的对应症状，当时原因尚未查明；本轮不把该历史现场归因为唯一原因。资源总量可在节点详情观察，但任务自身未获得具体的阻塞原因。

可选设计是对一组计算服务保留最小 worker 额度，或在会耗尽执行额度的部署前明确拒绝并说明影响。两者都比增加后台重试合理；不应临时提高常数来掩盖模型问题，也不需要自动杀服务。选择应以“一台支持的节点至少能推进一项已接纳任务”的产品契约为准。

## 架构评价

| 维度 | 当前评价 | 依据与取舍 |
| --- | --- | --- |
| 核心分层 | 清楚，应保留 | 从低到高为 Foundation、Kernel、Domain，CMake 和代码依赖向下；核心没有反向包含服务或插件实现。传输、进程、持久文件等机制与领域账户分开 |
| 服务划分 | 与业务状态所有权基本一致 | Market 拥有观测，Data 拥有历史版本，Task 拥有尝试与结果，Trading 拥有账户执行，Agent 拥有进程；计算在独立 worker。Task 不再链接回测/因子执行引擎 |
| 并发与生命周期 | 较扎实，局部语义交接仍有缺口 | 单一状态拥有者、串行持久线程、固定池、异步 RPC、发送许可和连接代次均落实；R2/R3 说明正确线程布局仍需正确的数据连续性与目标发布契约 |
| 交易事实 | 主要不变量明确 | 财务事实来自柜台；持久意图先于发送；未知结果继续占用风险；断线不重发；策略走统一路径。没有发现本轮路径绕过授权和风险插件直接报单，但这不是对全部执行路径的形式化证明 |
| 数据与实验 | 已具备可审计的固定输入模型 | 数据版本、来源、费用、规则和插件摘要固定；下载发布由 Task/Data 协调；行情取得时间不冒充历史公布时间。当前未知 PIT 是明确限制 |
| 持久化与恢复 | 主干合理，运行交付仍需补验 | durable_file、SQLite、产物摘要、分段日志与显式版本拒绝都有实现；备份范围是配对目录的冷备份。身份续期仍缺闭环 |
| 插件边界 | 实用且诚实 | 风控/数据提供方具备动态 ABI，算法与存储等按当前需要保留静态插件；插件是可信进程内代码。无需为了“全部动态化”增加抽象 |
| Terminal 边界 | 结构正确，端到端一致性需补齐 | C++ 编排在 native，Node-API 异步完成，UI 命令白名单与插件契约集中。R1、R5 分别是控制权限与读模型身份在跨层传递时丢失 |
| 版本政策 | 一致但有业务代价 | 只保留当前实现、旧格式明确拒绝，避免静默迁移。文件保留不等于旧结果仍可读取或重跑，不能对研究者承诺永久跨版本可复现 |
| 资源模型 | 有界且可观测，但并非完整活性保证 | 队列和载荷预算优于无限制接纳；静态预算不等于 RSS 上限，也不保证多服务组合仍能执行，见 R7 |

目前不建议拆出独立风控、订单、账户微服务，也不建议把所有服务合并回 Electron。前者会把当前账户内的一致性变成跨进程事务，后者会破坏安装版关窗后服务继续运行的要求。最小方向是在现有边界上修正少数不变量。

## 代码实现与维护成本

优势在于显式所有权、RAII、类型化领域与协议、边界异常转换、稳定错误码和双语诊断。测试重心在 C++ 与进程层，和项目真正的风险分布一致；依赖由 Conan/pnpm 锁定，CI 覆盖双平台、sanitizer、桌面安装副本及服务打包。敏感信息处理、持久化失败、交易不确定性普遍采用明确失败语义，未见为追求表面可用而自动重发交易的路径。

维护成本主要集中在几处高密度协调代码：Task Store 约 1715 行、CTP trader 1512 行、Agent 主文件 1448 行、协议 trading 转换 1100 行、LivePanel 1129 行。行数只是导航信号，不足以证明应拆分。应优先把“谁拥有哪一种状态、什么时刻允许副作用”说清，再按已有责任拆分；不要按文件大小机械制造一层类。

本轮三项 P1 的共同点并非缺少更多线程或保护分支，而是边界表达不完整：撤权没有穿透普通互斥；预热没有完成边界；数据连续性不是持久到裁决的事实。这些适合少量明确状态和定向回归，不适合继续在每个调用点补条件。

现有 UI 37 个用例相对业务面积仍集中在少数交互，尤其缺少同账户紧急控制、跨源读模型与迟到回复场景。需要增加的是这些不同风险的测试，而非补齐每个按钮或穷举全部参数。C++ 数值测试也应至少包含一组符合产品参数上限量级的高价格/长窗口组合。

开始时已有的程序副本清理改动与这些问题无关。本轮审阅未发现删除业务数据或仍被服务配置引用程序的直接路径：清理以已持久发布的服务引用为准，保留旧插件原始产物，只删除被替换且无人引用的程序与可重建插件目录。它并非全目录垃圾回收，过去已失去引用的副本和部分 CTP 库副本仍可能保留；这属于清理范围，不宜为此扩展成持久 GC 框架。当前相关新增用例包含在本轮全量 CTest 中。

文档记录很充分，但三份基线合计约 9600 行，读者难以区分“当时已完成”和“当前仍成立”。建议把本报告中的未闭环事项保留为当前索引，原阶段记录继续作为证据；后续完成项须链接当前测试，而不是在多个文档重复复制成功叙述。R6 是当前完成清单与代码不一致的具体例子。

### 研究结果应如何解释

主力连续、费用生效日和无 K 线交易日结算的近期改动解决了真实数据上的重要问题，不能再把这些功能说成未实现。固定输入、下一根撮合、前日持仓量选月和训练/留出分界也明显优于只有策略公式的演示工具。

仍须保留当前公开的限制：回测没有涨跌停成交约束；历史费率和合约规格尚未形成完整的自动版本化供给，已有券商费率查询、模板及部分数据表供给不等于完整历史；当前来源历史可知性未知；统计主力序列与可交易主力序列在少数换月时刻不同；不活跃品种需要使用者判断；每个因子截面参与条数可以不同。它们会影响研究结论的含义，不能用测试全绿消除，但也不应在本报告中冒充新发现的代码缺陷。

200000 根/点、单币种、20 个研究组合成员和固定策略集合是当前范围约束。成员指独立合约或品种单位，主力连续展开后的实际月份合计最多 256 个，并非只能使用 20 个月份。是否扩大应由实际研究任务决定；本次没有证据要求建设通用策略平台、流式计算框架、多币种或跨账户调度。

## 整改顺序与完成标准

1. **先修 R1–R3。** 验证同账户慢命令期间撤权能到达服务、启动预热不产生旧目标委托、同日行情重启首包没有完整 bar 时仍不越过缺口。按最小必要范围更新交易日志引擎标识与双语诊断，保留现有不重发和未知风险语义。
2. **修 R4、R5。** 宽整数比较解决均线中间值；来源身份解决图表旧回复。各增加一个能在旧实现上失败的定向用例。若策略执行语义变化，按规则核对实盘与回测引擎标识。
3. **完成 R6，裁定 R7 的产品契约。** 身份替换须用同一节点的既有数据验收；资源准入须展示不能推进的原因，并防止新增服务无提示地挤掉既有计算能力。
4. **再做真实仿真柜台和持续运行验收。** 按现有 CTP 清单核对登录、结算确认、报单撤单、真实回报、跨交易日和服务恢复。SDK 替身及源码审查都不能替代。
5. **冻结源码后做双平台交付验证。** 同提交 CI、Linux 服务包源码指纹、安装副本、目标 Linux 系统服务与实际安装、macOS 签名公证应对应同一可追溯版本。本轮报告不宣布这些已经通过。

本轮最合适的投入是修复少数跨边界正确性问题，并完成产品明确承诺的运行闭环。现有分层、进程主干、固定输入和账户所有权模型值得保留。
