# 项目评估与路线

日期：2026-10-28。评审基线：`ce20b5c6`（`main`）。

状态：方向已由使用者于 2026-10-28 确认，取代 2026-10-25 的评估与重构计划。**当前处于第 1 阶段**，第 0 阶段尚余 M0.1 与 M0.5。

本文回答三个问题：项目离目标有多远，最终形态是什么，按什么顺序走过去。
产品定义见[产品说明](../product.md)，交易不变量见[交易安全契约](../safety.md)。
第 9 节是执行状态，每完成一个工作包更新一行。

## 0. 结论

- 工程很严谨，但力气用错了地方。交易安全链、定点小数、期货账本和行情界面是对的，保留。
- 量化终端最核心的两件事还没做成：使用者不能自己写策略；产品从没在真实数据和真实柜台上跑过。
- 大部分代码花在“可追溯证据”、按任务复制的固定输入和多机部署上。它们让研究变慢、让 CI 变慢，还把内部模型暴露给了使用者。
- 方向：**C++ 管钱和单子，Python 管想法。** 策略是 Python 代码，回测、仿真柜台和实盘调用同一个接口；
  数据以自录 CTP 行情为主，存为 Parquet；进程按故障范围划分，删除管理层的大部分机制。
- 顺序：先接触现实，再换数据底座，再换策略与回测，再换实盘运行，最后是多因子组合和小资金实盘。
  每个阶段都用真实数据或仿真柜台验收。

## 2. 评价

### 2.1 保留

- **交易安全链。** 先记录后发送、一次性发送许可、结果不明不重发、授权和风控必经、每个账户一个独立进程。
- **期货领域细节。** 定点运算、逐日结算、保证金与手续费版本、主力换月、夜盘交易日归属，以及本根收盘决策、下一根成交。
- **行情界面。** 分组报价表和分时、K 线双窗格，已经是能用的看盘终端。
- **基础机制。** 持久写入、本机 IPC 与 TLS 通道、日志、Electron 安全加固，以及“每份状态只有一个拥有者”的原则。

### 2.2 问题，按严重程度

1. **策略不能自己写。** 使用者只能从写死的规则里选一个、填参数。策略页的“规则”只支持双均线；因子只有动量、期限结构、
   波动率三个，外加一个只能用收盘价的小表达式，而且已冻结。研究终端的核心价值基本缺失。
2. **从没接触过现实。** 交易文档写明只在测试用 CTP 替身上验证过，仓库里没有任何仿真柜台验收结果，本机开发节点没有下载过行情。
   正确性全部是对着夹具证明的。
3. **“可复现”做成了贯穿全栈的仪式。** 每个任务复制全部 K 线，于是有了 20 万根上限；螺纹钢一年的 1 分钟线就有约 8 万根，
   跨品种分钟研究放不下。快照、摘要、来源证据这些内部概念直接出现在界面上。
4. **部署拓扑按机房和团队设计。** Node Manager、SSH 远程登记、远程升级、联合卸载、冷备和制品摘要，一个人都用不上，
   却让 CI 变慢、故障面变大；Linux SSH 系统服务验收是 CI 里反复失败的一项。
5. **自动交易还不能真用。** 一个账户只能运行一个策略、一个合约；预热只用行情服务当天现场看到的 K 线，不读历史；
   行情服务或交易服务一重启策略就结束且不恢复；实时分钟线只在内存里，从不落盘。
6. **界面是表单向导，不是终端。** 回测是三步向导，结果是一长串折叠项，回测与评估分在两个模块；没有策略编辑入口，
   K 线上没有买卖点，没有参数敏感性图。
7. **需求写成了监管规范。** 2.6 万行、293 项功能需求、1,002 条验收，并规定“优先级不是排期、不自动删减范围”。
   一个人核对不了，AI 代理把它当法律执行，就会不停生成证据和校验机制。第 3、4 条的根源在这里。本次已删除，见第 8 节。
8. **反馈太慢。** 主干一个月没有全绿，一次 CI 一两个小时，累计改动量是现存代码的五倍多。代码产出远快于验证。

## 3. 目标形态

### 3.1 原则

- **C++ 管钱和单子：** 行情网关与录制、账户进程、风控、回测撮合与期货账本。
- **Python 管想法：** 策略、因子与研究、数据采集与整理。
- **策略只输出目标仓位或权重。** 换算整数手数、风控、记录、发送和全部金额计算都在 C++ 内核完成，规则见[交易安全契约](../safety.md)。
- **复现靠自动记录。** 每次运行记下数据版本、策略提交号、参数、引擎版本和依赖锁摘要，平时收在结果详情里。
- **只有一份契约。** 服务之间和界面都用 Protobuf；TS 类型和客户端由 proto 生成，不再手写 JSON 映射。
- **每个新机制都对应一个使用场景。**

### 3.2 进程

| 进程 | 语言 | 职责 | 来源 |
| --- | --- | --- | --- |
| 行情 | C++ | CTP 行情、分钟合成，向策略和界面分发 | 扩展现有 `asterion_market` |
| 录制，录制主机上一个 | C++ | 自己登录行情，订阅全市场，把 Tick 与分钟线存为 Parquet，收盘后合并；只读接口供 Terminal 与研究服务读取，不接受任何会打断录制的命令。由 systemd 直接看护，不受节点守护和 Terminal 管理 | 新建 `asterion_recorder`，与行情共用接入、聚合与写文件的代码 |
| 账户，每账户一个 | C++ | 授权、风控、先记录后发送、对账；接收策略目标并合并 | 扩展现有 `asterion_trading` |
| 策略，每个运行中的策略一个 | Python | 加载策略版本，历史预热，接收实时 bar，输出目标 | 新建 |
| 研究服务，每节点一个，暂名 `asterion_lab` | Python | 数据采集与仓库、回测与因子任务、运行记录、策略仓库索引；计算放子进程并行 | 新建，替换 Data 与 Research |
| 节点守护，每节点一个 | C++ | 拉起和监督上述进程、服务发现、远程节点的单一 TLS 入口 | 由 Node Agent 精简而来 |
| Terminal | Electron + React | 主进程持有服务连接，界面用生成的 TS 客户端 | 删除 Node-API 原生编排层 |

远程节点就是同一套程序在 Linux 上用安装包加 systemd 部署，Terminal 用一次性令牌配对。
Node Manager、SSH 登记、远程升级和联合卸载都删除。分析助手 `apps/services/research/reports/report.py` 已有 Python 端的
Protobuf 帧读写，可作为研究服务的起点。

### 3.3 数据

- **自录行情。** 行情进程按交易日把订阅合约的 Tick 写成 Parquet，并用同一份聚合代码合成 1 分钟线；目标是全市场。
  重启后续写，缺口如实记录，不补造。录制放在全天运行的 Linux 节点上。
- **Tushare。** 日线、合约表、交易日历和权限允许的历史分钟线，由研究服务采集。
- **存储。** Parquet 按数据类型、交易所、品种和交易日分区，DuckDB 查询。价格保留精确值，研究侧可读成浮点，账本只用定点。
- **数据集版本。** 一份分区文件清单。摘要在写入时计算一次，作为身份；任务只引用版本，不复制数据，也不设条数上限。
- **日历与交易时段。** 都带生效日期；夜盘的交易日归属按交易所规则。
- **主力连续。** 换月依据、换月时点和价格调整方式分别声明。连续序列只用于信号，成交落在真实合约上；
  调整后的价格和收益序列各有用途，不能混用。
- **多品种决策截点。** 多个品种一起决策时，哪些成员必须到齐、按谁的日历、迟到的 bar 怎么处理，写成确定规则，
  历史回放与实时运行一致，不默默用前值补齐。

### 3.4 策略与回测

- 策略放在使用者自己的 Git 仓库里，用任何编辑器和 AI 助手编写。策略版本就是提交号；工作区有未提交改动时另记差异摘要。
  Terminal 监视这个仓库，负责运行、展示、比较和上线。
- 接口初稿如下，M2.1 定稿：

  ```python
  class MaCross(Strategy):
      params = {"fast": 5, "slow": 20, "lots": 1}

      def on_bar(self, ctx, bar):
          closes = ctx.history(bar.symbol, "close", self.params["slow"])
          if len(closes) < self.params["slow"]:
              return
          up = closes[-self.params["fast"]:].mean() > closes.mean()
          ctx.target(bar.symbol, self.params["lots"] if up else -self.params["lots"])
  ```

  只在完整 bar 上决策，目标在下一根 bar 执行，与现有引擎一致。组合策略输出权重，
  内核按权益、价格和合约乘数换算成整数手数，向零取整，余量不自动分配。
- 回测：现有撮合与账本编成 Python 扩展模块，由 Python 驱动事件循环；参数扫描在多个子进程里并行。
- 快速研究：因子和信号探索直接用 Polars 和 NumPy 向量化计算；事件驱动回测负责验证。因子作为普通函数/包复用，统一输入输出和时点约定，不建立独立插件体系。
- 运行记录：每次运行一份记录；权益、成交、委托、持仓和逐日结算存 Parquet，列表和指标存 SQLite。

### 3.5 实盘运行

- 策略进程启动时从数据仓库加载历史预热，再接实时 bar；实时 bar 和历史 bar 由同一份聚合代码生成。
- 账户进程接受已登记策略实例的目标，合并为账户目标并保留归属；每笔委托走安全契约第 1 节的路径。
- 订单管理：限价、超时撤单重挂、最大追价跳数，按策略版本配置。
- 恢复：账户进程恢复交易记录，策略状态由预热重建；授权不跨重启。
- 监控：交易页的运行面板、桌面通知和可选推送；账户级和全局的“停止全部策略并撤单”。

### 3.6 界面

- 一级入口收为行情、研究、交易、数据四个，加设置。分析、策略、回测、评估四个一级入口删除。
- **研究页**：左侧策略和数据集，中间图表，右侧运行配置，底部运行记录。结果一屏看到核心指标、权益与回撤、
  带买卖点的 K 线、月度收益和参数热力图；回测、评估与比较在同一处；复现信息收在详情里。
- **交易页**：资金、持仓、委托、成交，以及运行中策略的面板：目标与实际仓位、最近信号、盈亏、风控占用、连接状态。
  “暂停新增”“停止并撤单”“平仓”分开确认。
- **数据页**：品种乘日期的覆盖矩阵、录制状态、采集任务。
- 文案使用量化术语：数据集、策略、参数、费用、结果。“固定输入”“来源证据”“内容摘要”这类内部概念不出现在主界面。
- 行情页保留现有设计。

### 3.7 文档

- 目标与不变量只有三份：[产品说明](../product.md)、[交易安全契约](../safety.md)和本文。
- 其余主题文档只描述当前代码，跟代码走：替换或删除代码的同一提交里更新或删除对应文档。
- 每个阶段开始时，把本文该阶段的验收清单细化成可执行步骤；阶段结束时在第 9 节记录真实验收结果。

## 5. 路线

每个阶段的出口条件都要求真实使用；只有夹具测试通过不算完成。

### 第 0 阶段：接触现实，1 至 2 周

目标：知道现有链路在真实环境里哪里会坏，并得到可信的 CI。不加功能。

| 工作包 | 内容 | 完成判据 |
| --- | --- | --- |
| M0.1 SimNow 交易验收 | 使用者提供 SimNow 账户；按 [CTP 仿真验收](../acceptance/ctp-simulation.md) 在交易时段运行 `tests/acceptance/ctp_trading.py`，再人工完成连接中断、进程恢复、跨交易日和 Terminal 关闭几项；只修验收暴露的问题 | 一份逐项记录通过、失败、未执行的验收记录；每个失败项都有修复提交或登记的已知问题 |

| M0.5 外部条件 | 使用者咨询穿透式认证流程，确认 Tushare 分钟线权限，准备一台全天运行的 Linux 主机 | 三项各有结论，写入第 6 节 |

### 第 1 阶段：数据底座，2 至 3 周

| 工作包 | 内容 |
| --- | --- |
| M1.1 Python 运行时 | 按决定 D1 选定分发方式；Python 与依赖由 uv 锁定；macOS 和 Linux 在没有系统 Python 的机器上都能运行 |
| M1.2 研究服务骨架 | Python 服务，沿用现有 Protobuf 帧格式与本机 Unix socket，远程沿用 TLS；由 Agent 监督；健康检查与日志 |
| M1.3 生成的 TS 客户端 | 由 proto 生成 TS 类型与客户端，Electron 主进程持有连接；第一个使用者是新的数据页，之后新增界面一律走这条路径 |

#### M1.7 统一部署结构与日志

使用者 2026-10-29 决定现在做，范围是全部 C++ 程序与 lab 服务。

**目录。** 根目录：Linux 主机 `/opt/asterion/`；Linux 桌面 `~/.local/share/asterion/`，macOS
`~/Library/Application Support/Asterion/`；开发环境换成 `asterion-development` / `Asterion Development`。每个程序一个目录：

```
<根>/agent/      bin/ lib/ config/ logs/ data/      节点身份、服务登记、Agent 状态在 data/
<根>/manager/    …                                   仅 Terminal 所在机器
<根>/market/     …
<根>/trading/    …                                   每个账户一个实例：data/<实例>/，日志文件名带实例
<根>/data/、<根>/research/  …                        同上，按实例分 data/
<根>/lab/        lib/python/（随包 Python）…
<根>/recorder/   …                                   录制主机
<根>/terminal/   config/ logs/ data/                 Terminal 程序本身仍在应用安装包里
```

插件（tushare、shfe、order_limits）与 CTP 库放在使用它的程序的 `lib/`。各程序的配置只在自己的 `config/`，安装时从仓库
复制一次，升级不覆盖。

**部署与升级。** Agent 把程序文件放进 `<根>/<程序>/bin|lib`（每个文件一次改名，与录制程序的 `setup.sh` 相同），取代
`artifacts/<sha256>.bin` 与 `services/<名字>/service.json` 的引用方式；某个程序的全部实例停下后才替换它的文件，交易
程序的升级仍要求账户先停止执行。实例登记（哪些实例、是否应运行）在 `agent/data/`。

**日志。** `log::init(<程序名>)` 读取 `<程序目录>/config/logging.json`，之后 `log::info("… {}", x)`、`warn`、`error`、
`debug`；`file.path` 支持相对路径（以程序所在目录为基准，如 `../logs/market-{pid}.log`）和绝对路径；控制台与文件各自
的开关、级别和 `pattern`。格式字符串不能按字段名脱敏，密码、令牌、授权码不得格式化进日志，评审时检查。

2. 安装目录：一个共用的“我的安装目录”函数；每个程序改为从它找配置、数据与库，删除对节点目录的依赖。
3. Agent：按程序目录部署、启动、升级与停止服务；实例数据与日志；插件与 CTP 库放 `lib/`。
4. 本机：安装器与开发环境按新结构建立根目录并放入程序；Terminal 原生层找 Agent、Manager 和服务的方式随之修改。
5. 远程：Linux 服务包按程序目录组织，SSH 登记与 `initialize-linux.py` 安装到 `/opt/asterion/`；录制程序并入同一根目录
   （`/opt/asterion/recorder/`）。
6. 测试与文档：单元、进程、端到端测试随目录修改；架构、服务、开发指南、录制文档更新。

**验收。** 全部 C++ 测试、界面检查与端到端测试通过；开发环境从空目录启动，行情、lab、交易（SimNow）各跑通一次；
远程服务包在 Ubuntu 24.04 容器中安装并启动；录制程序的发布脚本安装到新位置。

在新结构下照常运行，不做其他修改。

#### M1.8 局域网连接与独立交易服务

使用者 2026-10-29 决定现在做。行情、Data、Research、lab 和节点管理都在局域网内，不需要加密；只有交易服务可能在
局域网外（靠近期货公司前置的主机），又握有下单权，保留加密和双向身份验证。提前做第 3 阶段 M3.5 中与此相关的部分。

**局域网连接。** 远程连接一律是不加密的 TCP：Terminal、Manager 与远程 Agent、行情、Data、Research 之间都是。客户端连上后
先发 4 字节魔数 `ASTR`（`0x41535452`），服务端在读第一帧之前核对，不对就断开。魔数只防误连，不是密码：局域网里能连上
端口的机器都能发请求，包括让 Agent 部署和启动程序，防火墙只放行自己的机器，使用者已确认接受。Tushare 令牌由 Terminal
经本机 Unix socket 交给 lab，lab 没有远程实例，令牌不经网络。本机连接仍是 Unix socket，不变。

- 内核：魔数在 `RpcHost` 与 `RpcClient` 的明文 TCP 连接上统一处理，各服务协议不再各带魔数；录制程序改用它，删去
  `recorder.proto` 的 `magic` 字段，lab 的录制数据源随之修改。
- 删除：节点 CA 与证书签发、SSH 引导中的 mTLS 身份配置、“更换节点身份”、业务客户端证书（`trading-client.*`）、
  Terminal 连接设置里的证书文件，以及这些服务和客户端里的 TLS 参数。SSH 引导与 Agent 部署本身留到 M3.5。

**独立交易服务。** 只在 Linux 上，用自己的 `setup.sh` 安装，可以装在交易主机上，也可以装在 Terminal 所在的 Linux 机器上
（经 `127.0.0.1` 连接）。macOS 上的 Terminal 连接一台 Linux 交易主机，本机不再运行交易服务。

```
/opt/asterion/trading/
  bin/     asterion_trading、setup.sh
  lib/     ctp-trader.so
  config/  logging.json、tls/（服务端私钥与证书）、accounts/<账户>.json（端口、Terminal 指纹、CTP 账户与环境）
  logs/    每个账户一个日志文件
  data/    <账户>/ 交易记录
```

- 发布物是一个自解压脚本 `asterion-trading-setup.sh`，与录制程序同样构建、同样安装与升级（逐个文件改名替换，配置不动），
  以执行 `sudo` 的账户运行。每个账户一个 systemd 实例 `asterion-trading@<账户>`，`Restart=always`。
- `setup.sh` 增加、修改或停用账户实例：填写监听信息、Terminal 指纹、CTP 账户和柜台环境，并隐藏输入交易密码与授权码。停用只停止并禁用实例，交易记录原样保留。
  第一次安装时生成服务端私钥和自签证书，打印它的 SHA-256 指纹。
- 双向固定指纹：Terminal 第一次需要时生成自己的客户端私钥和自签证书（`terminal/data/tls/`，只有本人可读），在设置里
  显示指纹；交易服务只接受账户配置里写的指纹，Terminal 只接受连接设置里写的服务端指纹。私钥不离开各自的机器。
  不用 CA，没有到期续签；换证书就是重新生成并交换一次指纹。
- 交易时段（与录制程序相同的规则）不重启运行中的实例：升级的文件和配置立即放好，收盘后由定时器重启。重启使授权失效，
  这本来就是安全契约的规则。
- CTP 密码与授权码由 `setup.sh` 在交易主机本地隐藏输入，按账户保存为 systemd 加密凭据。服务初始化或重启时自动登录，不恢复委托授权；Terminal 不采集或传递凭据。
- 交易服务不再接受 Agent 的启动参数（`--owner-pid`、`--health-endpoint`、`--node-id` 等），由 systemd 看护；
  原来用节点身份的固定事实改用账户实例的身份。
- Terminal：设置里添加交易连接（名称、地址、端口、实例名、服务端指纹），连接后读取服务端账户；“开通交易”仅初始化该账户的风险政策。删除本机自动部署交易服务、Agent 的交易服务类型和 Manager 部署表单里的交易程序。
- 交易服务里的旧策略入口 `StrategyHost` 读本机行情服务，独立安装后不再有可靠的本机行情，提前在本工作包删除（原定第 2
  阶段删除，第 3 阶段由策略进程恢复）。此后实盘只支持手动下单，M0.1 验收脚本的策略部分随之去掉。
- 旧 Research 的“账户复核”经本节点 Agent 找到交易服务读取固定账户事实，交易服务独立后找不到也连不上它。使用者
  2026-10-29 决定提前删除（原属 M2.6）：账户复核任务、交易服务的固定事实归档与读取协议、对应界面一起删除。
  交易日志目录里原来放在 `facts/` 的独占锁文件改放 `owner/`。
- 交易服务的冷备份经 Agent 进行，交易服务独立后由交易主机自己备份 `data/`，Terminal 的数据备份不再包含交易账户。

**步骤。**

1. 内核：明文 TCP 的连接魔数；TLS 改为双向固定指纹、不用 CA。录制程序与 lab 录制数据源改用连接魔数。
2. 局域网服务：Agent、行情、Data、Research 的远程端点和 Manager、Terminal 的客户端改为明文加魔数；删除证书签发、
   身份更换和证书设置。
3. 交易服务：独立启动参数与账户配置；删除 `StrategyHost`；`setup.sh`、systemd 模板与自解压发布物。
4. Terminal：客户端证书与指纹、交易连接设置、在连接上开通与打开账户；删除交易服务的本机部署与节点绑定。
5. 测试与文档：错误魔数、错误指纹被拒绝的进程测试；`setup.sh` 的规则测试（同录制程序）；验收脚本改为连接独立交易服务；
   架构、服务、交易、录制、开发指南与 CTP 仿真验收文档更新。

**验收。** 全部 C++ 测试、界面检查与端到端测试通过；本机用 `setup.sh` 安装交易服务，从 Terminal 按指纹连接，在 SimNow

#### M1.10 去掉 Manager 与 Agent

**M2.2 回测引擎**（2026-10-31 使用者确认细化）

- 成交规则只有一份 C++ 实现：从旧 `engine.cpp` 抽出回放对象 `Replay`（本根决策、下一根执行，挂单只在下一根 bar
  有效，主力换月旧月按开盘平、新月接手，每日结算与权益记录），旧引擎改为调用它；Python 驱动循环：
  `replay.next()` 给出下一个时刻完成的各品种 bar（主力连续已复权），`step` 调用策略，`replay.decide` 把手数或
  权重交回 C++。与第 3 阶段策略进程向账户进程输出目标的形状相同。
- 目标换算（先平反向再开同向、权重按权益换手数向零取整）放在 `core/futures`，回测与 M3.2 的 Trading 共用；
  `paper_execution`、`replay_schedule`、`portfolio_targets` 与 `Replay` 移入 `core/futures`，旧 Research 链接它直到 M2.6。
- pybind11（Conan 锁定）编出 `asterion_engine`，针对随包 CPython 3.12 头文件构建并装入运行时；金额以 int64 原始值
  跨边界，不经浮点。

## 8. 工作规则

1. 只做当前阶段的工作包。第 4 节标为替换或删除的部分只接受当前阶段需要的修复，不加功能。
2. 工作包编号作为提交主题前缀，如 `M0.3`。一个提交只做一件事，改动尽量控制在几百行；跨模块重命名单独提交。
3. 每个工作包开始前写清三件事：使用者能看到什么变化，删除什么，哪项测试或真实验收证明它。
4. 每个新机制都要对应一个使用场景。不为“可能需要”添加摘要、证据、校验或兼容层。
5. M0.3 之后，快速检查是推送门槛，红了当天修复或隔离；完整检查每晚运行，失败登记到工作包。
6. 优先用录制回放代替手写替身：真实行情和柜台回报录下来，作为回放测试的基准。
7. 同一组件连续两次修正仍不收敛时，停下来重新设计，不继续打补丁。
8. 旧需求规格、旧目标架构和 10 月 21 日、25 日的两份评估已删除。仍然有效的实盘前安全门并入交易安全契约第 8 节，
