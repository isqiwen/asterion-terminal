## 2. 总体结论

**需求体系已较成熟，新架构方向正确。下一阶段的主要收益来自关键契约收口、规格一致性和交付排序，
而不是继续增加服务、通用平台层或横向功能。**

| 维度 | 判断 | 优化重点 |
| --- | --- | --- |
| 产品定位 | 个人国内期货研究与交易边界清楚 | 明确首个可用交付及运行责任模式 |
| 需求完整性 | 输入、状态、异常和验收覆盖充分 | 消除跨文档冲突，细化少数复杂语义 |
| 研究严谨性 | 可得时点、样本外、选择历史和固定证据考虑深入 | 连续收益、多品种共同决策和周期能力 |
| 交易安全设计 | 授权、未知结果、风险占用及恢复原则较完整 | 跨节点真实账户归属、值守失联及风险基准 |
| 服务划分 | 按状态与生命周期划分，整体合理 | 跨服务提交与恢复顺序 |
| 性能可靠性 | 有参考负载、测量方法及明确指标 | 工作集预算、停止能力和完整恢复计时 |
| UI与日常使用 | 页面和返回路径详细 | 用真实任务测量操作负担 |
| 全量交付 | 范围大，内部与外部依赖多 | 用有限范围的纵向闭环验证价值 |

需求数量、图稿数量、FR映射完整率只能说明覆盖组织情况，不能独立证明业务正确、使用方便或可交付。

## 3. 应保留的需求与架构决定

### 3.1 需求的实际优势

1. 事件发生、来源发布、取得、处理与策略可得时间分别保存，避免把今天获得的资料伪装成历史已知。
2. 连续合约作为研究信号，真实月份合约承担执行；历史规则按生效与可得条件解释。
3. 完整bar后决策，新单作用于后续bar；下一bar开盘估价不提前暴露整根bar成交量。
4. 训练、开发验证、最终留出与研究选择历史分开；复制项目、重命名、换频率不清除已观察事实。
5. 固定数据、策略包、实验、账户事实和评估之间有清楚的责任边界，修改产生新的内容身份。
6. 回测有效、模拟成功、行情已连接与实盘授权互不替代。
7. 暂停新增、撤单、平仓、停止运行和退出进程分别定义；未知结果不自动重发。
8. 情报限定材料、模型用途、外发预算、人工核验、更正与历史可得性；结构化基本面不必经过LLM。
9. 性能需求已有参考设备、规模、p95、取消时限、8小时持续运行与跨日场景。

主要依据：[共同契约](../requirements/common/contracts.md)、[分析范围](../requirements/modules/analysis/README.md)、
[回测时序](../requirements/modules/backtest/simulation.md#bar-execution-contract)、
[情报范围](../requirements/modules/intelligence/README.md)、[非功能基线](../requirements/common/reliability.md#quality-baseline)。
这些已有内容不应再次被列为“缺少时间语义、风控或可复现性”。

### 3.2 五类服务承载七个产品模块

| 服务 | 状态与职责 | 保留理由 |
| --- | --- | --- |
| Market | 实时来源连接、订阅、事件顺序与分发 | 行情连接可独立于历史仓库维护 |
| Data | 原件、历史数据、采集加工、快照、引用和发布 | 下载任务与发布决定归同一拥有者 |
| Intelligence | 提取候选、核验决定、事件发布与更正 | 有独立的长期状态和业务生命周期 |
| Research | 分析、策略、回测、评估及共同研究谱系 | 模块间直接调用，避免人为增加跨进程交接 |
| Trading | 账户执行许可、风险占用、订单与持久事实投影 | 按账户隔离运行，交易控制独立于重研究 |

Manager管节点，Agent管服务进程，业务载荷直连事实拥有者；系统任务中心只聚合，不能成为第二份任务库。
Research是后端进程，不新增一级产品导航。默认完整本机运行、远程可选，符合个人桌面产品定位。

回测、本地实时模拟和实盘共用适用的策略、领域与风控代码，各自隔离可变状态。
历史推进与柜台执行保留真实差异，共享代码不承诺真实成交与回测一致。

服务内有界线程池与异步I/O适合当前可信插件范围；取消采用协作停止，重启将未确认工作标为中断，
不自动重跑。线程不具备进程级崩溃隔离，这是已承认的取舍。冻结Python运行时可保留必要助手进程，
结果仍由业务服务确认，不恢复每次任务一个worker及第二套派发状态。

## 6. A02：真实账户唯一执行与实例绑定的保证不同

依据：[FR-LIV-RUN-04-05](../requirements/modules/live/operations.md#fr-liv-run-04-05)、
[交易文档](../trading.md)“账户记录与本机归属”、[目标设计](../architecture/target.md)“同一交易程序的跨节点实例管理”。

需求明确按稳定机构/环境/真实账户排除跨节点双执行；旧节点失联不等于停止，旧节点恢复也不能用旧身份发送。
目标架构描述账户固定绑定节点ID与服务实例ID；当前交易文档明确本机锁针对内部account_id，
不会自动识别两份配置是否对应同一外部资金账户。这是需求与架构保证之间仍须补齐的论证，
不是“需求没有考虑唯一执行”。

| 必须明确的问题 | 建议契约 |
| --- | --- |
| 同一真实账户如何识别 | 区分机构、柜台环境、投资者身份、内部account_id、连接资料和服务实例；显示名、前置地址、AppID变化不自动形成新资金账户 |
| 重复登记由谁裁决 | 指定唯一账户登记业务拥有者，说明并发登记与受管范围；不能每个节点各自批准 |
| 执行归属与授权 | 明确两者的持久事实及检查点，不以Terminal当前选择代替服务裁决 |
| 切换与旧方隔离 | 明确停止、在途核对、旧能力失效、重启检查和新授权；失联时无法排除旧方则拒绝新执行 |
| 保证范围 | 区分单一受管环境、多个独立安装和外部券商客户端；不可见外部指令不能宣称事前受控 |

本地文件锁、固定实例引用或一个归属序号，不能单独证明跨主机排他性。需要真实的权威裁决与旧方隔离依据。
不将账户业务状态塞入Manager，不引入自动主备或超时抢占。若首期无法满足安全迁移，应明确收紧支持范围，
不能保留迁移承诺而只完成实例选择UI。

最低验收：同一外部账户两份配置、两个节点、两个观察窗口并发请求；一个有效归属；旧方失联不能接管；
完成有效隔离和新授权后，旧节点恢复不能发送旧意图。只读观察不构成新的执行者。

## 7. A03：值守需要可执行的监控断连契约

依据：[操作旅程](../requirements/workflows/README.md)开头及JRN-040约1752行、
[实盘运行](../requirements/modules/live/operations.md)约1137、1625、1869行、
[运行监控与退出](../requirements/common/contracts.md#attended-operation-contract)。

旅程要求约定监控连接中断时暂停新增风险；运行页允许“仅关闭窗口，后台继续”，值守输入主要是确认布尔值。
两者可以兼容，但监控身份、失效时间、检测方和恢复权限尚需形成同一契约。

以下为待确认建议：

| 事件 | 建议行为 |
| --- | --- |
| 关闭工作区或隐藏窗口，监控通道仍有效 | 服务继续，清楚显示后台运行及残余风险 |
| Terminal进程退出且无其他有效监控端 | Trading按固定失联政策暂停新增风险 |
| 监控端与Trading失联 | Trading判断失效并执行限制，不能依赖失联UI完成安全动作 |
| 使用者主动离开 | 显式暂停，处理或接受已展示的在途订单与持仓状态 |
| 监控恢复 | 恢复观察；交易恢复仍经过核对与明确批准 |

固定监控会话身份、失效阈值、时间依据、判断方、限制范围和恢复条件。
这里的业务监控条件不恢复已删除的任务worker心跳租约。
后台进程可以继续运行，同时策略不再新增风险；失联不自动撤单、平仓或补发。

有人值守是重大产品选择，应在总纲及启动页面突出。远程Linux执行不自动等于无人值守支持；
若以后改变责任模式，须独立评审凭据、失联、告警、跨日和重启恢复，而非只加一个推送按钮。

## 8. A04—A06：量化计算与周期契约

### 8.1 连续价格、收益与风险缩放

依据：[数据交付范围](../requirements/modules/data/README.md#scope-data)、
[连续序列](../requirements/modules/data/processing.md#fr-dat-prc-01-04)、
[分析计算口径](../requirements/modules/analysis/README.md)、
[有限波动率缩放](../requirements/modules/strategy/portfolio.md#volatility-scaling)。

数据支持不复权/价差后复权；分析标签使用P(t+h)/P(t)−1；组合波动率从信号价格计算简单收益。
现有规格已经禁止复权价格直接成交，但还应固定调整锚点、差值日期、累积方向、跨换月收益和方法适用范围。

算术例：100到110的简单收益是10%；整段加100后，200到210的简单收益为5%。
加性调整不保持百分比收益，因此即使未用于成交，也可能改变标签和仓位缩放的含义。

| 内容 | 声明用途 |
| --- | --- |
| 调整后的信号价格 | 趋势、价差或其他明确支持的特征 |
| 按明确换月规则构造的收益序列 | 收益标签和波动率等；标明口径与局限 |
| 真实合约成交及账户收益 | 模拟账本、绩效与实盘核对 |

建议补一个单次换月的5—6行算例，覆盖调整前后、信号值、收益标签、真实合约和账户结果。
同时保留已有历史可得限制；不能为统一图表而让未来换月修订进入旧实验。

### 8.2 多品种共同决策截点

依据：[决策时钟](../requirements/common/contracts.md#decision-clock-contract)、
[策略逻辑](../requirements/modules/strategy/logic.md)“完整K线边界与事件消费”、
[模拟时序](../requirements/modules/backtest/simulation.md#bar-execution-contract)。

已有固定输入截点、跨流排序和延迟输入不能倒填的原则。需要细化的是共同截点如何关闭：
哪些成员和周期必须齐备、采用谁的交易日历、同名义bar异步抵达何时截止，以及缺成员时整组跳过还是明确允许部分决策。

不同夜盘收盘时段使这些问题更加实际。先选择有限且确定的规则，写入固定策略包；
不以最后抵达的消息偶然决定输入集，不默默用前值补齐。
验收用两个合约、不同交易时段及一根迟到bar，比较历史与实时驱动下的输入集合、决策次数和输出。
无需新增服务或通用水位框架。

### 8.3 周期能力贯穿全链路

数据可聚合5/15/30/60分钟；策略逻辑和[回测范围](../requirements/modules/backtest/README.md)明确限定1分钟与日线。
这不是直接矛盾，但“图表支持15分钟”容易被理解为“可完整运行15分钟策略”。

建议增加采集粒度、特征周期、决策周期、撮合粒度、实时模拟及实盘能力矩阵。
针对个人中低频研究，优先评估下列组合；15分钟是本报告建议，不自动扩大现行需求。

| 数据粒度 | 特征/决策周期 | 撮合粒度 | 用途 |
| --- | --- | --- | --- |
| 日线 | 日线 | 日线 | 首条易核对的研究闭环 |
| 1分钟 | 15分钟 | 1分钟 | 中低频决策与更细执行模拟 |
| 1分钟 | 1分钟 | 1分钟 | 保留既有频率，不强迫所有策略使用 |

新增周期须同步明确交易时段聚合、完整边界、预热和输入可得规则。
完整bar模型本身是已披露的简化：日线成交反馈在bar完成后可见会影响盘中处置表达。
评估报告应固定展示决策粒度、反馈粒度、成交估价和容量假设，用实时模拟解释偏差，不把它当真实成交复原。

## 9. A07—A08：组合归属与风险基准

### 9.1 成交归属必须有有限、确定的政策

依据：[FR-STR-PRT-01-03](../requirements/modules/strategy/portfolio.md#fr-str-prt-01-03)。
现有需求正确规定每账户一个具有执行权的组合实例、目标净额与真实归属分别守恒。
甲目标+4、乙目标−1、账户目标+3，只能确定聚合目标，不能唯一确定真实成交与费用归属。

需明确：只成交2手分给谁，费用和尾差如何分摊，人工介入怎样处理，成员退出怎样处置，
已存在仓位和未成交意图如何参与下一次分配。内部目标抵消不能伪造成柜台成交或不存在的多空仓位。

首期选择一套足够用的确定性分配规则，列出适用与拒绝条件，不建设通用虚拟账户平台。
保存原目标、聚合目标、真实成交、成员归属、未归属项和费用。研究与实盘使用同一固定政策。
以同向/反向目标、部分成交、费用更正、人工交易和暂停成员的一组完整算例验收。

### 9.2 风险基准与持久状态

依据：[账户政策](../requirements/modules/live/accounts.md)约894行、
[运行风险](../requirements/modules/live/operations.md)约1445—1464及1562—1584行。
已有日内损失/回撤基准和日切政策要求，但示例忽略现金进出，需要补有限的现金流调整公式和恢复状态契约。

Trading最小持久风险状态应明确有效政策、业务期间/基准、已确认现金流调整、必要高水位、
触发原因与时点以及解除依据。具体字段以选定方法为准，不为所有理论风控预建通用状态框架。

- 入金不能直接掩盖已发生亏损。
- 出金不应误记为交易损失。
- 重启不能重新选择有利基准或丢失风险暂停。
- 重新授权不能自动解除尚未完成审查的限制。

用入金、出金、日切、重启和重新授权的连续算例验证；该风险能力启用前完成，不另设独立风控服务。

## 10. A09：跨服务引用与发布的提交和恢复

依据：[目标架构](../architecture/target.md)“数据、状态与跨模块交接”“引用与删除”。
稳定身份、内容拥有者登记引用、删除时重查、离线不当作无引用等原则已经正确。
下一步应把两类副作用写成可实现的协议：Research/Trading固定对象与Data引用登记；
Intelligence发布决定与Data固定内容公开。

| 阶段 | 契约需要回答 |
| --- | --- |
| 开始 | 谁生成稳定操作身份，重复相同操作怎样查询 |
| 准备 | 各方先持久保存什么；内容准备不等于业务公开 |
| 确认 | 哪个持久事实代表提交成立，何时对外显示可用 |
| 回复丢失 | 按原身份查询，不产生第二次发布或固定对象 |
| 中途失败 | 哪些内容可见、哪些仅为待确认，恢复由谁推进 |
| 解除引用失败 | 保留哪些证据，维护入口如何核实，不超时自动删除 |

特别处理“引用登记成功但消费对象未提交”形成的残留：既不能自动当垃圾删掉，也不能无限积累而没有核对入口。
跨服务未知状态先明确其可见性与继续路径，不引入全局扫描服务、第二权威数据库或通用分布式事务平台。

最低验收：每个持久步骤前后中断、回复丢失、重复查询、内容拥有者离线、删除与固定引用竞争；
结果要么完整可用，要么明确待确认，不破坏既有引用。

## 11. A10—A12：资源、取消与恢复指标

依据：[质量基线](../requirements/common/reliability.md#quality-baseline)、
[NFR-RUN-01](../requirements/common/reliability.md#nfr-run-01)、
[NFR-REC-01](../requirements/common/reliability.md#nfr-rec-01)、[目标架构](../architecture/target.md)服务内执行章节。

### 11.1 两个任务不等于资源有界

参考环境为16GiB内存、1000万根分钟线、20特征、两项研究并行，总RSS峰值目标12GiB。
容量估算而非实测：1000万行×20个float64×8字节=1.6GB，约1.49GiB；两项约2.98GiB，
尚未计原始bar、标签、排序/回归中间副本、Python、Data和Electron。
这不能证明目标无法达成，但证明仅限制任务数量不足以说明总体资源上界。

按有限算法集合明确预计工作集、分块读取、临时副本和缓存上限；控制Polars/BLAS等内部线程，
避免两项任务各自占满CPU。由所属服务落实排队/拒绝，Agent继续只观察资源，不新增全局资源预留表。
测量Data更新、两项研究、行情和Trading的组合负载；多Research实例不能自动沿用单实例结论。

### 11.2 取消按执行阶段验证

NFR要求请求反馈≤1秒、可控计算停止≤30秒、外部阻塞≤60秒。服务内线程不能安全强杀，
需把每类能力映射到可停止机制：

| 阶段 | 最小机制与验收 |
| --- | --- |
| 内置回测/因子循环 | 有限粒度取消检查点，测实际返回和名额释放 |
| 外部来源请求 | 有界超时，明确取消能否中断等待以及剩余最长时间 |
| Python助手 | 既有受控进程的超时/退出规则，结果仍由所属服务确认 |
| 不满足契约的插件 | 不能标为满足该停止时限的正式能力，明确适用范围 |

超时后显示待核实保持真实性，但不等于通过停止时限验收。
结果确认与执行都结束后才释放并发；不因取消UI响应而提前开启下一项大任务。
不恢复每任务worker、租约或自动重跑。

### 11.3 恢复必须包含初始化阶段

NFR-REC-01当前写“服务可用后60秒内显示目录和未决任务”，未约束可能很慢的账本恢复与就绪前阶段。
建议分别定义从进程启动到状态查询可用、目录及未决任务可见、允许接纳新工作三个时间。
使用10万条索引及明确的历史事件量，记录实际重放与核对工作。
先测量，再决定是否需要进一步优化；不直接添加另一套快照或缓存机制。

## 12. A13：明确故障与维护代价

### 12.1 Agent仍是共同故障点

[服务文档](../services.md)约19—20行规定：Agent异常退出时受管进程一并退出。
因此管理面不承载业务流量，不等于Agent故障不会中断Trading。
保留现有共同停止语义可以成立，但应明确故障影响矩阵：新增发送停止、柜台在途订单不因此撤销、
恢复先核对、进程恢复不恢复授权、不补发未知意图。
将重研究和真实交易放在不同节点可作为部署选择，但不能被描述成高可用或自动接管。

### 12.2 整体同发行升级是维护耦合

[安装需求](../requirements/modules/system/setup.md)约155—189行明确全部已登记节点在线预检、停机、同发行升级，
并承认升级不是跨机器原子事务。此选择对个人小规模系统可以接受。
代价是长期离线研究节点可能阻止整体升级，研究与交易共享维护窗口。
应在部署及升级预览中显示范围、受阻节点和未完成状态；不以本机成功冒充整体完成。
本报告不据此要求滚动升级、历史协议兼容或自动清除离线登记。

## 13. A14：交付切片与外部能力实证

基线需求正文有65条REQ：22条P0、43条P1；P2为0。
[产品范围](../requirements/product.md)明确优先级不是排期，[交付规格](../requirements/delivery.md)明确不自动删减范围。
这不是分类逻辑错误，而是全量范围不能直接驱动首版交付。
现有目标架构已采用纵向闭环，建议补每阶段支持集合、外部条件和可交付终点。

| 阶段 | 建议交付内容 | 完成判据 |
| --- | --- | --- |
| 1. 契约与真实数据范围 | A01—A05关键规则、首批品种/期间/来源 | 选定实验有行情、必要历史规则和明确用途证据 |
| 2. 数据研究闭环 | Data接管采集，Research接管计算；一个日线规则策略及简单固定权重组合 | 固定数据→策略包→回测→评估全程可核对 |
| 3. 模拟执行闭环 | 相同策略包进入本地实时模拟及CTP仿真 | 决策差异可解释，未知订单、跨日、暂停恢复成立 |
| 4. 分钟与多品种 | 评审15分钟决策/分钟撮合，联合输入、部分成交归属 | 历史与实时使用相同周期、缺失及分配规则 |
| 5. 实盘与远程 | 唯一执行归属、监控失联、远程故障和维护 | 所有受影响安全条件有实际证据后启用 |
| 6. 研究扩展 | 更多模型、混合策略、情报提取与事件研究 | 每项扩展完成真实用户任务而非只有入口 |

建议让简单策略的实时模拟闭环先于完整情报系统，以更早检验数据、固定包、执行规则和评估能否协同。
此顺序不删除多因子、模型或情报的完整目标；最终阶段划分须落实到正式交付计划。
每阶段均满足其依赖的P0条件，不能用分期推迟已启用能力的安全要求。

外部数据实证应提前，沿用GATE-DATA，不新建另一套准入框架：

| 核验对象 | 实证内容 |
| --- | --- |
| 首批品种与区间 | 合约、行情频率、历史覆盖、缺口与修订 |
| 历史规则 | 乘数、步长、交易时段、手续费、保证金、有效日期及来源依据 |
| 时点可得性 | 历史发布/取得证据及只能事后分析的限制 |
| 来源条件 | 授权用途、额度、费用、分页、限流及异常响应 |
| 允许业务 | 可探索、可严格回测、需研究假设、可模拟、可实盘分别列明 |

正确的拒绝规则不能替代可获得的数据。不能等页面全部完成后才发现主路径缺必需输入，
也不能为获得一条可跑通路径而把研究假设冒充真实历史证据。

## 14. A15：减少个人研究的操作成本

依据：[UI设计](../requirements/common/ui-designs.md)、[交互规范](../requirements/common/interaction.md)、
[操作旅程](../requirements/workflows/README.md)。现有规格已经规定上下文携带、草稿保留、任务原页反馈和返回路径，
58项UI不等于58个独立窗口。优化应建立在这些规则上。

- 保持数据、情报、分析、策略、回测、评估、实盘的七模块导航，系统为辅助入口。
- 原页展示任务进度和结果，任务中心作为聚合辅助，不成为计算完成的必经跳转。
- 继承固定数据、策略和实验上下文，只要求补真实缺项。
- 从失败结果直接定位输入、字段或业务条件；返回保留筛选、草稿和选择。
- 在已有工作区提供最近研究、明确下一步与缺项面板，不另建业务层级。

可用性验收选少量高频任务：已有数据和配置下修改参数重跑、复核一个失败实验、定位并处置待核对订单。
分别记录首次/重复耗时、操作数、重复输入数及错误率，先建立真实试用基线再设目标，不凭空承诺分钟数。
正确性完善后，日常操作成本直接影响个人使用价值。

## 15. 高价值验收场景与文档落点

### 15.1 验收围绕业务不变量

| 场景 | 应证明的结果 |
| --- | --- |
| 同一真实账户重复配置、跨节点请求、旧节点复活 | 单一有效执行归属，未知旧方不自动接管 |

| 训练标签越界、来源修订 | 越界标签排除，旧实验固定内容不被覆盖 |
| 组合负载下取消、恢复与交易控制 | 实际停止、资源和控制延迟分别满足指标 |
