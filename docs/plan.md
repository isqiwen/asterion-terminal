### M3.93 回测覆盖与就绪口径

- 分钟回测按请求范围、交易日历和合约存续期核对日线、结算价与分钟覆盖；日线明确零成交的日期允许无分钟，其余缺少分钟时停止并列出缺口，不能用日结算记录补成成功结果。不完整分钟的排除范围也必须可见。
- 未就绪时不发新目标，已有持仓保留，与 Trading 一致：`ready=False` 之后的 K 线不再按旧目标下单，直到策略再次就绪并给出目标。
- 回测的单笔上限与实盘一致：超过单笔上限的目标拆成几笔，而不是被风控拒绝。
- 移除纸面账户的历史累计委托数限制，保留现有在途风控，支持一年分钟线回测。

完成检查：30 个交易日只有第一天有分钟线时，运行失败并列出缺失日期；日历缺段、某开市日同时缺日线和分钟线时也失败并列出日期；上市前、摘牌后和已确认零成交的日期不误报缺分钟；多合约异步到达、滚动验证切换和主力换月时，未就绪后不再用旧目标下新委托，已有仓位继续结算，重新就绪并给出新目标后恢复；6 手目标在单笔上限 5 时成交 5 手和 1 手；补齐一年所需的真实分钟线、日历、合约及交易参数，固定版本完成回测并核对覆盖与排除范围。

真实单日回测、5＋1 手拆单、夜盘交易日以及有日线但缺分钟时的失败提示已验收；一年真实分钟线回测待做。

### M3.85 拆分 Market 与 Warehouse

三类服务各管一件事：Market 分发实时行情，Warehouse 采集、整理和提供历史数据，Trading 执行交易。理由：行情进程不含下单代码，不接触实盘账户和实盘资金；Warehouse 不连接柜台，不持有任何柜台凭据。

1. **改名**：原来的合并服务只保留历史采集和数据仓库，成为 Warehouse。
2. **拆出 Market**：行情连接、合约目录和报价流移到 `apps/services/market/`，使用单独的行情账户；Warehouse 不再连接 CTP。两者之间没有任何通信，Terminal 分别连接两个服务。

### M3.84 统一数据服务

把各来源的历史数据整理成一份固定版本的数据，用固定接口提供；实时行情另行分发。当时两者在同一个服务里，M3.85 拆分后历史数据归 Warehouse，实时行情归 Market。不录制 Tick 和分钟线，理由见[产品说明](product.md)。

```text
Market：CTP → 实时行情 → Terminal
Warehouse：Tushare → 交易所 → gtja → 新浪财经 → 入库 → 来源仓库 → 合成 → 统一数据 → 读取 → Lab / Terminal
```

- **对外统一**：客户端按表、交易所或合约、日期范围读取和请求数据，不选择也不依赖来源；每个分区记录来源，只用于追溯。
- **内部补缺**：一次请求按优先级依次经过各来源，只补前面来源没有的分区；某个来源失败不影响其他来源，已取得的数据保留。
- **优先级**：

| 表 | 顺序 |
| --- | --- |
| 日线 | Tushare → 交易所 → 新浪财经 |
| 分钟线 | Tushare → 新浪财经 |
| 合约表、交易日历 | Tushare |
| 结算参数 | 交易所 → Tushare |
| 最小价位 | 郑商所 → gtja |

按以下顺序完成：

1. **移除录制**：删除 Tick、分钟线和观测段录制、合并、自录发布及分钟对比。
2. **统一接口**：协议去掉来源，Terminal 数据页和 Lab 同步修改；日线统一按交易日分区，才能逐日补缺。
3. **补缺**：请求按优先级经过各来源；接入新浪财经。AKShare 是 Python 库，Warehouse 不依赖 Python，所以直接请求它使用的公开接口。
4. **发布边界**：已改为只合成启动时及已结束任务提交的固定来源版本，重试也遵守同一边界。
5. **状态写入失败**：保留可查询的失败状态和错误；存储恢复后，在下次提交时补写失败记录，再继续接纳任务，不重发来源请求。

现有 Tushare 配置已可采集合约表和交易日历，六张表的基础采集及固定版本到单日回测的链路已通过。待核验历史分钟接口的权限和覆盖，并从 Warehouse 内部来源清单核对真实补缺结果。

完成检查：A 结束、B 仍在运行且已提交来源批次时，A 触发的统一版本只纳入已结束任务的数据；B 成功、失败或取消后，其已保留的数据才可发布；无变化不生成新版本，旧版本仍可读。任务状态持续写入失败时，旧失败可查询，新任务不接纳；恢复存储后同一服务可接纳新任务，旧请求不重发，已提交的来源版本不重复通知。真实请求一段日期，确认 Tushare 缺失部分由公开来源补齐且内部清单记录正确来源；修复后在部署服务重验。用 Trading 记录的 K 线与统一数据比对（M4.0b 之前）。

## 第 5 阶段：小资金实盘（M5）

真实资金账户第一次下单前，以下各项都要完成并留下记录：
- 仿真浸泡（M3.6、M4.4）每天对账一致。
- 通过期货公司的穿透式认证，取得 AppID 和授权码。
- 按 [Trading 部署约束](trading/deployment.md)完成账户唯一执行者和主机迁移验收，确认全部旧实例停用后再启用新主机。
- 日内亏损和回撤限额：正确处理出入金、换日、重启和重新授权。
- 告警覆盖实例结束、委托被拒、未确认委托、连接中断、风控触发和对账不一致；“停止全部策略并撤单”演练通过。

然后用小资金连续运行一个月，每天对账，没有解释不了的差异。

## 待定问题

- 策略用到 Tick 或五档盘口时，购买历史数据还是开始录制。
- 策略包只含源码和准备时刻，不记来自哪次回测；实盘与回测对照需要这条关联。是否在从运行准备策略包时带上运行 ID，交易页据此打开那次回测（参考 MLflow 模型版本记录来源运行，不引入别名和阶段）。
- 风控是否增加资金/保证金占用、日内亏损和撤单次数限制（M5 之前决定）。
- Warehouse 的旧数据集版本永远保留。版本本身只多一张清单，但重采替换下来的数据块因旧版本仍在引用而一直占用磁盘。是否加清理：保留最近一段时间和回测用过的版本，其余连同只被它们引用的数据块删除；回测记录在本机 Lab，需要设计如何让 Warehouse 知道哪些版本被用过（磁盘紧张时再定）。
- Tushare 分钟线是否把集合竞价和收盘 tick 并入相邻 K 线，与 Trading 聚合的分钟 K 线是否一致（M4.0b 之前核实）。
- 回测排除不完整分钟，Trading 仍交付跨越行情中断的 K 线；需明确统一规则，并验证断线前后策略输入（M4.0b 之前决定）。
- 在 GitHub 的 Ubuntu runner 上，渲染进程崩溃后，内核把 core 管道给 systemd-coredump 时进程一直不退出，Terminal 也就不退出；CI 已改掉 `core_pattern`。还不清楚普通 Linux 桌面是否同样会卡，需要在装了 systemd-coredump 的机器上试一次。
- 桌面测试偶尔在关闭 Electron 时超时（“did not release its process channels”），约一成，功能步骤都已通过；未抓到现场，可能与上一条同源。
- 实盘预热只用 Trading 自己聚合的 K 线（交易规则第 7 条）：日线策略上线要先观察够均线长度那么多个交易日，改参数或换策略包又要重来，Trading 重启期间的 K 线永久缺失。是否允许把固定数据版本里的一段历史随策略包显式发布，只用于预热、不执行目标（M3.6 之前决定；改规则由使用者决定）。
- 回测缺少交易所费率就停止：大商所、中金所、广期所的全部品种，上期所和能源中心 2024-07-22 之前、郑商所 2015-09-30 及以前，现在都不能回测。在来源补齐之前，是否允许某次运行显式填写费用假设，并在结果上标明“费用为假设”。
- 回测按决策那根 K 线的收盘价挂限价、等价格回来才成交；实盘在下一根开始时按对手价立即成交。分钟线上差别不大，日线遇到跳空时回测不成交、实盘追价成交。是否把回测改为下一根开盘价成交（换月已经这样做），或做成运行选项。
- 告警只在 Terminal 开着时有。实盘前需要交易主机自己能把实例结束、放弃批次、未确认委托和连接中断发出去；用什么渠道（M5 之前决定）。
- `get_account` 每秒返回当日全部委托和成交，再经三次 JSON 转换到页面；一天上千笔委托时会拖慢交易页。是否改成只返回在途委托和计数，其余分页读取（M4.3 之前决定）。
- 行情页主连的 1 分钟图在回放行情下价格上下剧烈跳动，同时标题显示“暂无新报价”；需确认是否混入了其他月份的报价。
