# 开发计划

本计划列出开发顺序、当前状态和各阶段的验收条件。产品目标见[产品说明](product.md)，交易要求见[交易规则](safety.md)。标记“使用者”的事项需要真实账户、凭据、签名或部署环境。

## 设计约定

- 研究读取 Market 合成的固定研究数据集，分区来源规则见 [History](history/README.md#仓库与固定版本)。
- 分钟 K 线按时钟边界聚合；支持周期见[通信协议](protocol.md#4-公共类型)。
- 仿真浸泡先使用固定月份合约，自动换月在多品种组合阶段之前完成。
- 实例重启只重放该实例自己的行情记录，账户授权遵守[交易规则](safety.md)。

## 第 3 阶段：仿真运行验收

### M3.4 客户端收敛

页面已使用生成的 Protobuf 类型，原生层通过 `trading.call`、`market.call` 和 `market.watch` 管理连接并转发消息。隔离桌面验收和模拟全市场性能检查已完成。

剩余验收：连接真实 Market，在开发桌面打开全市场行情，记录消息大小、界面处理耗时和交互响应，确认持续更新时界面流畅。

### M3.82 历史参数补齐

#### 实现与验收

按以下顺序完成：

1. **完成链路隔离**：已完成。
2. **历史按需补采**：以请求的品种、日期范围和频率为输入，由 Market 自动检查覆盖、补采并保存进度，失败恢复限定在已接纳的需求内；分别处理整日缺失和已有分区内的不完整数据。核验 Tushare 历史参数接口的实际覆盖，补充请求范围内公开归档缺失日期的来源。Terminal 展示进度、覆盖和错误，Lab 只读取固定版本。
3. **固定版本消费参数**：Lab 按合约和实际交易日读取价位变化，参数缺失或冲突的区间停止回测，后续补齐保留已有版本。

验收：取得参数变化前后的真实分钟数据，确认夜盘按交易日切换价位，改变当天最终高低价或后续行情不影响此前的委托与成交；供应商恢复后完成已接纳范围的补采。

### M3.85 拆分 Quotes 与 History

三类服务各管一件事：Quotes 分发实时行情，History 采集、整理和提供历史数据，Trading 执行交易。理由：行情进程不含下单代码，不接触实盘账户和实盘资金；历史数据服务不连接柜台，不持有任何柜台凭据。

1. **改名**：Market 改名为 History，行为不变。
2. **拆出 Quotes**：行情连接、合约目录和报价流移到 `apps/services/quotes/`，使用单独的行情账户；History 不再连接 CTP。两者之间没有任何通信，Terminal 分别连接两个服务。

### M3.84 统一数据服务

Market 只做两件事：分发实时行情；把各来源的历史数据整理成一份固定版本的数据，用固定接口提供。不录制 Tick 和分钟线，理由见[产品说明](product.md)。

```text
CTP → 实时行情 → Terminal
Tushare → 交易所 → gtja → 新浪财经 → 入库 → 来源仓库 → 合成 → 统一数据 → 读取 → Lab / Terminal
```

- **对外统一**：客户端按表、交易所或合约、日期范围读取和请求数据，不选择也不依赖来源；每个分区记录来源，只用于追溯。
- **内部补缺**：一次请求按优先级依次经过各来源，只补前面来源没有的分区；某个来源失败不影响其他来源，已取得的数据保留。
- **优先级**：

| 表 | 顺序 |
| --- | --- |
| 日线 | Tushare → 交易所 → 新浪财经 |
| 分钟线 | Tushare → 新浪财经 |
| 合约表、交易日历 | Tushare |
| 结算参数 | 交易所 |
| 最小价位 | 郑商所 → gtja |

按以下顺序完成：

1. **移除录制**：删除 Tick、分钟线和观测段录制、合并、自录发布及分钟对比。
2. **统一接口**：协议去掉来源，Terminal 数据页和 Lab 同步修改；日线统一按交易日分区，才能逐日补缺。
3. **补缺**：请求按优先级经过各来源；接入新浪财经。AKShare 是 Python 库，Market 服务不依赖 Python，所以直接请求它使用的公开接口。

验收：真实请求一段日期，Tushare 缺失的部分由公开来源补齐并记录来源；用 Trading 记录的 K 线与统一数据比对（M4.0b 之前）。

### M3.6 两周仿真浸泡（使用者）

- 在 SimNow 用固定月份合约的策略连续运行两周，每天收盘后核对成交、持仓和资金。
- 期间演练：关闭 Terminal；停止 Market 和 Lab；行情断线（实例应继续运行）；Trading 重启后热重启并重新授权；柜台断线。
- 每天记录对账结果，以及每处不一致和原因。

第 3 阶段完成条件：浸泡期间每天对账一致；上面的演练都按预期运行。

## 第 4 阶段：多品种组合

### M4.0b 实盘换月

目标：实盘实例可以交易主力连续（例如 `SHFE/rb`），合约到期前自动移仓；策略看到的连续历史与研究一致（M4.0a 的复权）。

- 换月判断与研究相同：前一交易日持仓量最大的合约，只向后换。实盘从 Trading 自己的行情读取持仓量。换月日先平旧合约、再开新合约，都走同一条执行路径。
- 下一个月份必须在账户白名单内；不在时，换月前结束实例并提示。

完成标准：实盘隔离测试跨过一次换月后，持仓在新合约上，策略历史连续。

## 第 5 阶段：小资金实盘（M5）

真实资金账户第一次下单前，以下各项都要完成并留下记录：
- 仿真浸泡（M3.6、M4.4）每天对账一致。
- 通过期货公司的穿透式认证，取得 AppID 和授权码。
- 按 [Trading 部署约束](trading/deployment.md)完成账户唯一执行者和主机迁移验收，确认全部旧实例停用后再启用新主机。
- 日内亏损和回撤限额：正确处理出入金、换日、重启和重新授权。
- 告警覆盖实例结束、委托被拒、未确认委托、连接中断、风控触发和对账不一致；“停止全部策略并撤单”演练通过。

然后用小资金连续运行一个月，每天对账，没有解释不了的差异。

## 待定问题

- 策略用到 Tick 或五档盘口时，购买历史数据还是开始录制。
- 风控是否增加资金/保证金占用、日内亏损和撤单次数限制（M5 之前决定）。
- Tushare 分钟线是否把集合竞价和收盘 tick 并入相邻 K 线，与实盘和录制的分钟 K 线是否一致（M4.0b 之前核实）。
- 回测排除不完整分钟，Trading 仍交付跨越行情中断的 K 线；需明确统一规则，并验证断线前后策略输入（M4.0b 之前决定）。
- 任务状态写入失败后，该任务留在 `Manager` 中，后续提交都报错，只有重启 Market 才恢复；录制不受影响。是否改为自动恢复（M3.6 之前决定）。
- 郑商所 2022-01-04 的结算参数旧表没有“手续费收取方式”列，现有结算适配器读取失败；需核对旧格式并恢复这类历史费用采集。
- 端到端场景 `research-lab` 偶尔在全量运行时找不到两次运行的对比列，单独运行稳定通过（M3.6 之前查明）。
