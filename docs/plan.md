# 开发计划

本计划列出开发顺序、当前状态和各阶段的验收条件。产品目标见[产品说明](product.md)，交易要求见[交易规则](safety.md)。标记“使用者”的事项需要真实账户、凭据、签名或部署环境。

## 设计约定

- 研究读取 Market 合成的固定研究数据集，分区来源规则见 [Warehouse](warehouse/README.md#仓库与固定版本)。
- 分钟 K 线按时钟边界聚合；支持周期见[通信协议](protocol.md#4-公共类型)。
- 仿真浸泡先使用固定月份合约，自动换月在多品种组合阶段之前完成。
- 实例重启只重放该实例自己的行情记录，账户授权遵守[交易规则](safety.md)。

### M3.82 历史参数补齐

#### 实现与验收

按以下顺序完成：

1. **完成链路隔离**：已完成。
2. **历史按需补采**：已完成。Warehouse 按请求的品种、日期范围和频率只取缺的分区，失败时保留已取得的数据，再次提交补齐缺口；Terminal 展示进度、覆盖和错误。新浪分钟线最早一天的 `partial` 分区不再重取，理由：新浪只能回溯约两个交易日，之后也取不到完整数据。待核验 Tushare 历史参数接口的实际覆盖（使用者）。
3. **固定版本消费参数**：已完成。Lab 按合约和实际交易日读取价位变化，参数缺失或冲突的区间停止回测，后续补齐保留已有版本。
4. **历史手续费**：Warehouse 自动从可靠来源采集和补齐；补不到的保留缺失，依赖它的回测停止。不用零值、当前费率或推算代替，也不增加人工导入。已完成交易所部分：上期所和能源中心 2024-07-22 之前的文件没有平今手续费，入库为缺失；郑商所 2015-09-30 及以前的文件只有保证金，手续费缺失。待做：
   - 已接入 Tushare `fut_settle`，排在交易所之后补缺：保证金率和手续费按其文档示例（上期所 2018-11-14）的单位读取，平今手续费入库为缺失。待用 token 核验（使用者）：覆盖哪些交易所和年份；大商所、中金所、广期所的单位是否与上期所相同；`offset_today_fee` 是费率还是每手金额。核验前，Tushare 补来的参数因缺平今手续费不能用于回测。
   - 大商所、中金所、广期所自己的结算参数文件还没接入。已查：大商所官网有按日期查询的结算参数页（含手续费、收费方式和保证金率），但本机请求它、现用的日线接口和官网首页都返回 HTTP 412，推测是要求浏览器执行脚本的访问限制，服务主机上多半相同；中金所 `sj/jscs/<年月>/<日>/index.xml` 在已试的日期都是空表；广期所尚未找到公开地址。
   - 已完成：Lab 回测按合约和交易日读取固定版本的交易所保证金率和手续费，缺失时停止，不再填写每次运行的费用。结果：上期所和能源中心 2024-07-22 之前、郑商所 2015-09-30 及以前，以及大商所、中金所、广期所的全部品种，在补齐来源之前都不能回测。

验收：取得参数变化前后的真实分钟数据，确认夜盘按交易日切换价位，改变当天最终高低价或后续行情不影响此前的委托与成交；供应商恢复后完成已接纳范围的补采。

### M3.97 逐笔成交记录与跨日复盘

交易记录保存柜台回报的逐笔成交（成交编号、价格、手数、成交时间和交易日），换日不清除；交易页按交易日查历史成交。理由：对账和实盘与回测对照都要逐笔价格和时间，内存里的成交换日就没了。

完成检查：重启和换日后仍能查到前一交易日的逐笔成交；同一成交重复回报只记一次。

### M3.96 多合约 K 线不互相阻塞

统一回测和 Trading 在不同交易时段、停报及行情中断时的交付规则：一个合约休市或停报不阻塞其他合约，不伪造缺失合约的 K 线，同时保留正常同桶行情的对齐。理由：当前所有合约必须共同越过时间桶，停报会使整个实例积压并结束。

完成检查：两个合约中一个停报或休市，另一个持续交付、实例不结束；恢复后不重复交付旧时间；回测与 Trading 对同一行情序列给出一致输入。

### M3.95 实例告警归账户状态

实例失败和放弃批次的通知由 Terminal 的账户状态层发出，与交易页是否打开、当前选中哪个账户无关；同一事件只通知一次，Terminal 启动后第一次读取到的失败也通知。

完成检查：停在行情页时实例失败，收到通知；切换账户再切回不重复通知；Terminal 启动时已失败的实例通知一次。

### M3.94 研究源码草稿归工作区

未保存的修改属于工作区：切到结果再切回、运行回测后自动切页，草稿都在。运行时有未保存修改，先保存再运行，并提示已保存；保存失败则不运行。理由：回测必须用看得见的代码，记录的源码副本才是真的。

完成检查：改一行不保存，运行回测，结果对应改后的代码，回到编辑器修改仍在。

### M3.93 回测覆盖与就绪口径

- 分钟回测按请求范围、交易日历和合约存续期核对覆盖；缺少应有交易日的分钟数据时停止并列出缺口，不能用日结算记录补成成功结果。不完整分钟的排除范围也必须可见。
- 未就绪时不发新目标，已有持仓保留，与 Trading 一致：`ready=False` 之后的 K 线不再按旧目标下单，直到策略再次就绪并给出目标。
- 回测的单笔上限与实盘一致：超过单笔上限的目标拆成几笔，而不是被风控拒绝。
- 移除纸面账户的历史累计委托数限制，保留现有在途风控，支持一年分钟线回测。

完成检查：30 个交易日只有第一天有分钟线时，运行失败并列出缺失日期；策略未就绪后不再用旧目标下新委托；6 手目标在单笔上限 5 时成交 5 手和 1 手；一年分钟线回测跑完。

### M3.92 策略执行的暂停、批次替换与拆单

- **暂停**：在柜台发送许可检查处生效。正在写盘或排队待发送的开仓记为未发送；已开始发送的委托按柜台回报处理，减仓照常执行。
- **批次替换**：新目标或平仓替换未完成的一批时，旧委托因发送依据失效而退出时，不清掉替换它的一批。
- **拆单**：目标执行按合约手数单位拆分，每笔不超过单笔上限，一笔成交并核对持仓后再从实际持仓规划下一笔；价格、总持仓和在途委托检查不变。

完成检查：`StrategyTarget` 回归测试覆盖写盘与 SDK 排队期间暂停、写盘期间平仓或换目标、单笔上限 5 或 5.5 时 6 手开仓和平仓；全量构建及 `ctest --preset conan-debug -j 6` 通过。真实验收在 M3.6：SimNow 上暂停后不再开仓，超过单笔上限的平仓拆单完成。

### M3.91 行情页版式

市场视图一行顶栏放分类、品种概览或全部月份、表头设置和行情状态，去掉“⋯”浮层；分组行情表按窗口宽度排成几列，每组不拆开；右侧只留一个图表，周期在同一排切换；按代码添加自选放进自选分类；“上能源”改称“能源中心”。取消“合约”视图：它的五档、当日数据和同品种其他月份放到右侧图表下面，右侧可以展开成大图。理由：原来左三右二的固定分列一边很长一边空，宽屏把表格拉得很稀；两个图表窗格常常一个是空的；连接状态藏在浮层里，打开还会挡住图表；“合约”视图和市场右侧重复，看五档要来回切换。

### M3.90 数据页按表组织

数据页始终显示最新数据，不显示版本；左侧列出各张表、已采集合约、采集任务和版本历史，右侧只显示选中的一项，从历史或回测记录打开旧版本时醒目提示并可回到最新数据；服务器地址和磁盘余量在设置的数据服务里；采集在对话框里，表已定，只问这张表需要的范围和日期。理由：原来八张卡片从上到下排列，同一张表的摘要、覆盖、采集和任务分在四处，表单还要随表切换字段。

### M3.89 历史 K 线从行情页移到数据页

行情页只放实时行情，去掉实时／历史切换；已采集合约的列表和 K 线放到数据页。理由：这份数据来自 Warehouse，采完在同一页就能看，已到期的合约也有入口。图表窗格的“历史 K 线”保留，看交易中的合约时可以往前翻。

### M3.88 服务改名为 Market 与 Warehouse

三个远程程序叫 Market、Warehouse、Trading，界面继续叫行情、数据、交易。理由：程序名说明它做什么，Market 和 Warehouse 比 Quotes 和 History 更贴近职责；界面名说明用户在看什么。已部署的旧服务要卸载，再装新包；服务主机上的目录和凭据路径随之改变，Terminal 里的地址要重填。

### M3.87 Terminal 与服务的协议核对

Terminal 和服务分开安装。每个服务报告自己 `.proto` 的哈希，Terminal 读状态时比对。用哈希而不是版本号或 commit，理由：`VERSION` 目前不变，查不出差异；commit 每次提交都变，改文档也会误报。Trading 不一致时只提醒，不阻止操作，理由：不能因此失去撤单和平仓。

### M3.86 Terminal 行情接收

1. **图表**：每个合约各存最近 512 条报价。理由：全市场共用时，交易时段不到一秒就会被其他合约挤掉。
2. **隐藏窗口**：窗口隐藏时行情、数据页和交易账户照常读取，Electron 不节流后台计时器。理由：切回来不应先看到旧数据或未连接，Tick 图也不应断档；页面一直在读，原生层不会积压。
4. **订阅与报价状态**：状态行显示已确认订阅数和提交总数；单个合约 30 秒没有新报价显示“暂无新报价”，整个行情源 30 秒没有任何报价才显示“行情未更新”。理由：冷门合约本来就少有报价，原来满屏的“行情未更新”掩盖了真正的中断。
3. **连接错误**：状态行下显示最近一次失败原因。理由：连上之后证书变了或服务拒绝时，页面只会一直重连，看不出等待是否有用。

本机推送暂不做：服务端 250 毫秒组帧加页面 500 毫秒取帧，最坏约 750 毫秒，等 M3.4 用真实行情测过再定。

### M3.85 拆分 Market 与 Warehouse

三类服务各管一件事：Market 分发实时行情，Warehouse 采集、整理和提供历史数据，Trading 执行交易。理由：行情进程不含下单代码，不接触实盘账户和实盘资金；Warehouse 不连接柜台，不持有任何柜台凭据。

1. **改名**：原来的合并服务只保留历史采集和数据仓库，成为 Warehouse。
2. **拆出 Market**：行情连接、合约目录和报价流移到 `apps/services/market/`，使用单独的行情账户；Warehouse 不再连接 CTP。两者之间没有任何通信，Terminal 分别连接两个服务。

### M3.84 统一数据服务

Market 只做两件事：分发实时行情；把各来源的历史数据整理成一份固定版本的数据，用固定接口提供。不录制 Tick 和分钟线，理由见[产品说明](product.md)。

```text
CTP → 实时行情 → Terminal
Tushare → 交易所 → gtja → 新浪财经 → 入库 → 来源仓库 → 合成 → 统一数据 → 读取 → Lab / Terminal
```

- **对外统一**：客户端按表、交易所或合约、日期范围读取和请求数据，不选择也不依赖来源；每个分区记录来源，只用于追溯。
- **内部补缺**：一次请求按优先级依次经过各来源，只补前面来源没有的分区；某个来源失败不影响其他来源，已取得的数据保留。
- **优先级**：

| 表 | 顺序 |
| --- | --- |
| 日线 | Tushare → 交易所 → 新浪财经 |
| 分钟线 | Tushare → 新浪财经 |
| 合约表、交易日历 | Tushare |
| 结算参数 | 交易所 → Tushare |
| 最小价位 | 郑商所 → gtja |

按以下顺序完成：

1. **移除录制**：删除 Tick、分钟线和观测段录制、合并、自录发布及分钟对比。
2. **统一接口**：协议去掉来源，Terminal 数据页和 Lab 同步修改；日线统一按交易日分区，才能逐日补缺。
3. **补缺**：请求按优先级经过各来源；接入新浪财经。AKShare 是 Python 库，Market 服务不依赖 Python，所以直接请求它使用的公开接口。

验收：真实请求一段日期，Tushare 缺失的部分由公开来源补齐并记录来源；用 Trading 记录的 K 线与统一数据比对（M4.0b 之前）。

## 待定问题

- 策略用到 Tick 或五档盘口时，购买历史数据还是开始录制。
- 策略包只含源码和准备时刻，不记来自哪次回测；实盘与回测对照需要这条关联。是否在从运行准备策略包时带上运行 ID，交易页据此打开那次回测（参考 MLflow 模型版本记录来源运行，不引入别名和阶段）。
- 风控是否增加资金/保证金占用、日内亏损和撤单次数限制（M5 之前决定）。
- Warehouse 的旧数据集版本永远保留。版本本身只多一张清单，但重采替换下来的数据块因旧版本仍在引用而一直占用磁盘。是否加清理：保留最近一段时间和回测用过的版本，其余连同只被它们引用的数据块删除；回测记录在本机 Lab，需要设计如何让 Warehouse 知道哪些版本被用过（磁盘紧张时再定）。
- Tushare 分钟线是否把集合竞价和收盘 tick 并入相邻 K 线，与实盘和录制的分钟 K 线是否一致（M4.0b 之前核实）。
- 回测排除不完整分钟，Trading 仍交付跨越行情中断的 K 线；需明确统一规则，并验证断线前后策略输入（M4.0b 之前决定）。
- 任务状态写入失败后，该任务留在 `Manager` 中，后续提交都报错，只有重启 Market 才恢复；录制不受影响。是否改为自动恢复（M3.6 之前决定）。
- 端到端场景 `research-lab` 偶尔在全量运行时找不到两次运行的对比列，单独运行稳定通过；失败时对比区显示其中一次 `getRun` 返回“请求无效”（M3.6 之前查明）。
- 在 GitHub 的 Ubuntu runner 上，渲染进程崩溃后，内核把 core 管道给 systemd-coredump 时进程一直不退出，Terminal 也就不退出；CI 已改掉 `core_pattern`。还不清楚普通 Linux 桌面是否同样会卡，需要在装了 systemd-coredump 的机器上试一次。
- 桌面测试偶尔在关闭 Electron 时超时（“did not release its process channels”），约一成，功能步骤都已通过；未抓到现场，可能与上一条同源。
