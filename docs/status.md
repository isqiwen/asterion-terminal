## 当前能力

| 模块 | 当前实现 |
| --- | --- |
| Terminal | macOS Apple Silicon 与 Linux x86_64；Electron + React + Native；启动检查、独立设置窗口、中英文；UI 工作区统一编译，按需挂载 |
| 行情 | CTP 合约目录、订阅、自选、五档、分时、分钟线和涨速；Lightweight Charts 绘图；无来源内容明确不可用 |
| 历史数据 | Tushare 分钟与全市场表；SHFE 历史保证金的已核验窄范围；独立 Data 仓库、固定快照、具名组合、覆盖核对和显式单分区重取 |
| 数据证据 | 来源隔离、内容摘要、受限日线原始响应、SHFE 双报表证据；同值重取可保存独立观测；日线原文只读质量核对 |
| 回测 | 四条单合约与三条排序规则；组合账本、逐日结算、换月、费用/风控、留出及滚动评价；固定结果资金与预算解释、合约/月度贡献、日期精度持有期；Polars 收益对齐、QuantStats 扩展统计、skfolio 最小方差组合研究 |
| 因子 | 价格动量、期限结构、波动率；单序列或 3–100 条序列截面；可选滞后流动性资格；逐观测实际成员、因子值、标签收益和分组证据 |
| 实验管理 | Task 固定输入、尝试、结果；显式重试、固定/新快照派生、来源与名称备注、2–3 项比较（日线因子含留出与逐轮验证）、单项及比较 JSON 证据导出；有限动量参数派生和滑点变体 |
| 账户交易 | 每账户独立服务、授权与白名单、持久记录后发送、限额与价格检查、未知委托核对、断线不重发；共享策略规则；账户事实不依赖窗口生命周期 |
| 服务与插件 | Node Agent 管部署、进程和资源；本机 Unix Socket、远程 Linux TCP+mTLS；原生数据与风控可独立安装和固定摘要，UI/静态模块按现有契约构建 |

## 范围与限制

- 当前仅期货 Terminal；远程服务仅 Linux x86_64。没有独立 Web、移动端或用户 CLI。
- 生产历史来源为 Tushare 和 SHFE；SHFE 当前仅 `SHFE/au/2025-12` 的 2025-10-20 至 2025-10-22 保证金，不能推广为全市场历史覆盖。来源没有数据时不补造。详情见[数据](market-data.md)。
- 表分区支持显式单分区重取，不提供批量/定时重取、物理删除或自动依赖清理。不同来源和版本不会自动拼接；日期覆盖不等于日内完整性，完整历史时段和严格时点可得性仍缺来源证据。
- 实时分钟线来自本次行情服务观测，重启后重新开始；1 分钟界面可按来源显式分段浏览，不能自动当作已发布历史档案。
- 回测固定费用模型与历史保证金来源各有范围；更广历史费率、手续费单位、期货公司加收、盘中调整和历史规格仍未完整覆盖。部分最小价位来自成交价推断，不能冒充交易所公告。单合约日线支持显式结算阶段调整；具体适用条件见[回测](backtest.md)。
- 回测没有完整涨跌停成交限制，不模拟所有交易所微观结构。组合为单币种、保证金按合约相加，没有跨品种优惠。日期精度持有期不代表盘中精度；含未平仓的完整合约收益归因和换月成本分解仍有限。
- 回测和因子合计输入上限各为 200,000 条。因子没有中性化或训练预处理框架，尚无分块读取；因子分组标签收益不含交易成本，不等同账户收益。日线因子比较核对评价边界、预热、实际观测和成员，不重算共同样本或合并滚动相关系数。
- 组合研究对 2–3 个独立回测收益流拟合配比并在后段验证，与等权对照；不转换期货手数、不模拟共享保证金或组合再平衡费用，不使原有选优数据成为新的样本外证据。
- 实验导出含固定参数、结果和身份摘要，不含完整原始输入、行情、插件及可执行程序，不是独立复现包或生产数据导入格式。
- 实盘当前只有限价单；真实券商/仿真柜台与跨交易日持续运行仍需专门验收。隔离 CTP SDK 通过不能证明真实柜台通过；没有自动交易接管或断线重发。
- UI 模块随应用发布，没有第三方 UI 包安装器。策略、存储和 CTP/执行仍为静态模块；没有全模块动态化计划、通用依赖解析、任意热替换、多风控组合或远程插件选择界面。
- 每个 Task 最多 1,000 个活动任务，终态释放活动额度并保留记录。恢复使用当前结构、原实例身份与配对；不迁移、改写或删除不支持的用户数据。冷备份须包含 Data/Task 及依赖，不支持在线或任意跨路径恢复。
- 节点和线程容量有界，但不构成硬 RSS 上限或任意峰值延迟承诺。多账户真实回报峰值、物理整机故障、全节点满载及更多 Linux 桌面环境仍需独立证据。
- `Decimal` 的八位小数定点范围约为 ±922 亿，超范围明确失败；浮点仅用于展示与非权威统计。

## 下一步

1. 按实际平台完成发行安装、签名/公证和真实柜台验收；每轮重新核对源码、服务包和 Native 资源身份。
2. 在明确数据来源、范围和额度后补齐历史费用、规格、交易时段与可知性事实，不通过猜测或新增兼容层补齐。
3. 用真实负载证据决定是否需要分块或并发优化，保持账户、数据、任务的单一状态所有权。
4. 有实际独立交付需求时再设计新动态能力，优先完善现有 SDK 和明确 UI 贡献点。
